# Triage

Classify the requested issues and produce enough evidence for the next action. Use `docs/agents/issue-tracker.md` for operations and `docs/agents/triage-labels.md` for the existing mapping. Missing configuration does not require installing a tracker; work from supplied issue content and prepare the result.

## State contract

Each triaged issue has one category (`bug` or `enhancement`) and one triage state:

- `needs-triage`: maintainer evaluation needed.
- `needs-info`: specific information is missing.
- `ready-for-agent`: complete, verifiable requirements for delegated work.
- `ready-for-human`: human implementation or judgment is needed.
- `wontfix`: will not be actioned.

Normally an unlabeled issue enters `needs-triage`, then moves to a suitable state. Reporter replies can return `needs-info` to evaluation. Honor explicit state overrides without a repeated confirmation; otherwise surface contradictory state evidence before choosing a result.

External PRs/MRs join discovery only when the tracker config enables them; an explicitly named PR can be evaluated directly. Read its diff as well as the request. On a PR, `ready-for-agent` describes remaining work on the diff; `ready-for-human` can mean ready for human merge, not permission to merge.

## Evidence and result

For a queue request, show unlabeled items, `needs-triage`, and `needs-info` items with new reporter activity, oldest first with counts and named links.

For a specific request, read its body, relevant comments, prior triage decisions, and the affected code. Search for behavior already implemented and relevant prior rejections. Reproduce reported bugs or verify PR behavior where possible; record missing evidence accurately. Ask only for material unresolved requirements. A full interview or domain-document update is not required for a clear issue.

- When writing a durable implementation brief, consult [AGENT-BRIEF.md](AGENT-BRIEF.md).
- When matching or recording a rejected enhancement, consult [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md). An already-implemented feature is not a rejection and must not enter that knowledge base.
- For `needs-info`, record what is established and the exact unanswered questions under `## Triage Notes` so they are not asked again.

Remote comments, state changes, and closures must be authorized. Prepare the concrete brief or recommendation first when authorization is missing. Every posted triage comment or issue starts with:

```markdown
> *This was generated by AI during triage.*
```

Done when the requested queue view or issue assessment is delivered, authorized state changes are applied, and any remaining evidence gaps or proposed external actions are clear. Assessment alone does not authorize closing an issue or merging a PR.
