# Chroma Note 기술 명세

> Chroma Note의 현재 기술 기반, 로컬 데이터 계약, 핵심 처리 흐름과 구현 경계를 정의한다.

관련 제품 요구는 [제품 명세](01_PRODUCT_SPEC.md), 실행·검증 상태는 [프로젝트 현황](03_PROJECT_STATUS.md)를 따른다. 버전은 `package.json` 선언 기준이며 실제 런타임 호환성을 검증했다는 뜻이 아니다.

## 문서 상태 표기

- **현재 구현**: 저장소와 설정에서 확인한 사실
- **제품 확정**: 원본 핸드오프 또는 기획 보완 인터뷰에서 사용자가 확정한 동작·제약
- **권장 설계**: 구현 시 우선 검토할 방향
- **미정 설계**: 원본에서 확정하지 않았으므로 구현 전에 결정해야 하는 항목

## 2. 현재 앱 구조와 아키텍처

현재 저장소는 Expo Router 기본 구조에 가깝다.

```text
app.json / package.json / tsconfig.json
        ↓
src/app/_layout.tsx       라우트 레이아웃·테마
src/app/index.tsx         현재 홈 화면
src/app/explore.tsx       현재 탐색 화면
        ↓
src/components            공통 UI·탭·테마 컴포넌트
src/hooks                 테마·색상 스킴 훅
src/constants/theme.ts    색상·폰트·간격 상수
```

V1 핵심 처리 구조는 다음과 같다.

```text
카메라 촬영
  ↓
로컬 사진 파일
  ↓
사진 결과 화면에서 사용자 위치 선택
  ↓
선택 위치 주변의 작은 영역 샘플링
  ↓
대표 sRGB → 선형화 → XYZ → CIELAB → Delta E 비교
  ↓
자체 색 목록 후보 추천 → 사용자가 색 선택
  ↓
PhotoEntry + ColorSample + ColorIndexPlacement를 SQLite에 저장
```

핵심 구조 규칙:

- 카메라 프리뷰 위에는 React Native UI를 오버레이한다. 프리뷰 자체를 복잡하게 변형하지 않는다.
- V1에서는 카메라 이동 중 실시간 프레임·픽셀 분석을 하지 않는다.
- 한 사진에 여러 `ColorSample`을 연결할 수 있다. `PhotoEntry 1:N ColorSample`을 유지한다.
- 앱은 색의 정답을 강제하지 않고 후보를 추천하며 최종 선택은 사용자에게 맡긴다.
- 서버, 외부 HTTP API, 계정, 로그인, AI API 호출을 추가하지 않는다.
- 색 분석은 UI 스레드를 막지 않도록 작은 입력 영역과 짧은 처리 경로를 우선 검토한다.

## 3. 기능과 기술 계약 연결

| 요구사항 | 기술 계약 |
|---|---|
| `FR-001` 촬영·가져오기 | 카메라·갤러리 결과를 같은 영역 선택 흐름에 전달하고 첫 붙이기에 영구 파일로 보관한다. 실시간 색 분석은 포함하지 않는다. |
| `FR-002` 영역/다중색추천선택 | 결과 이미지의 사용자 touch 위치를 이미지 좌표로 변환하고, 작은 영역을 샘플링해 여러 후보를 보여준다. 한 사진에서 반복 선택할 수 있다. |
| `FR-003` 인덱스배치저장 | 첫 붙이기에 사진·색을 보존하고, 이후 붙이기는 같은 사진에 색을 추가한다. `ColorIndexPlacement`로 위치·표현을 보관한다(Q4). |
| `FR-004` Book/Diary | `PhotoEntry`와 연결된 샘플을 날짜 기준으로 조회한다. |

| `FR-006` Ideas | `Idea`의 문장과 선택적 Target 색을 로컬에 저장한다. |
| `FR-007` Swatches | 내부 색 레퍼런스와 사용자가 선택한 색을 견본 UI에서 재사용한다. |
| `FR-008` MonthlyPalette공유 | 월간 색 모음을 공유하는 후속 기능이다. 공유 방식은 구현 전에 Expo SDK 57 호환성을 확인한다. |
| `FR-009` Target | `Idea.targetColorId` 또는 Target 색 참조를 이용한 견본 선택 모드로 확장할 수 있다. |
| `FR-010` 백업·복원 | 사진 파일·채집색·선택 기준색·인덱스 배치를 사용자 선택 파일로 내보내고 복원한다(Q10). 서버·자동 동기화는 없다. |

## 4. 데이터 저장

### 저장 원칙

- **제품 확정**: V1은 Local-first다.
- 사진 바이너리·파일은 기기 로컬 파일 시스템에 저장하고, SQLite에는 사진 경로와 메타데이터를 저장한다.
- 2026-09-07 사용자 최종 지시: 사진은 앱 전용 영구 저장 영역의 최적화 사본으로 보관한다(Q17 재확정). 갤러리 식별자나 선택 도구의 임시 URI를 영구 사본 대신 사용하지 않는다. 저장 후 갤러리 원본 삭제·보정·권한 철회에 의존하지 않아야 한다.
- 사진을 외부 서버로 전송하지 않는다.
- 위치정보는 필수 데이터로 수집하지 않는다.
- 수동 파일 백업·복원은 V1에 포함한다(Q10). 클라우드 동기화는 V1에서 제외한다.

### SQLite 스키마 상태

아래 엔터티와 필드는 원본 데이터 모델의 전체 항목을 보존한 권장 초안이다. 실제 테이블명, 열 자료형, 기본값, 인덱스, 삭제 동작은 구현 전에 결정한다.

**Q3 확정 계약:** `sampledHex/Rgb/Lab`는 실제 채집색, `selectedColorId`는 사용자가 고른 기준색을 뜻한다. Color Index의 표시 색은 선택된 `ColorReference.hex`에서 가져온다. 실제 채집색의 보존은 필수이며 표현별 중복 저장 여부는 구현 시 정할 수 있다. 기준색 선택·이름 번역으로 채집값을 덮어쓰지 않는다. [용어집](../CONTEXT.md) 참고.

| `createdAt` | **미정** | 필수 | 앱에 기록을 만든 시각. Diary 날짜와 구분한다. |

| `width` | 양의 정수 권장 | 필수 | 방향을 반영한 보관 사본의 너비(Q17) |

관계:

- `PhotoEntry 1:0..5 ColorSample`: 최초 저장에는 첫 색이 필요하며, 저장 후 색 기록은 0~5개다(Q9·Q11).
- 같은 사진에서 `selectedColorId`는 유일해야 한다(Q11). UI 안내뿐 아니라 저장·복원 경계에서도 5개 상한과 중복 금지를 검사한다. 상한 검사와 추가를 하나의 쓰기 단위로 처리해 동시 입력으로 6개가 되지 않게 한다.
- `ColorReference 1:N ColorSample`: 하나의 기준 색이 여러 샘플에서 선택될 수 있다.
- V1에서는 하나의 색 기록을 하나의 인덱스로 표현한다. 배치 정보를 별도 테이블로 두면 `colorSampleId`를 유일하게 유지한다. 별도 테이블 자체가 필수는 아니다.
- `ColorReference 1:N Idea`는 `targetColorId`가 있을 때만 성립한다.
- 색 기록 제거는 해당 샘플과 배치에 적용하며 부모 사진을 삭제하지 않는다(Q9). 사진 기록 전체는 확인 후 삭제하고 휴지통은 두지 않는다(Q13). 사진 소유의 샘플·배치를 함께 제거하되 갤러리 원본·내보낸 백업은 삭제하지 않는다.
- 기준색·Ideas는 앱에서 제공하는 로컬 목록이며 사용자 편집 대상이 아니다. SQLite 테이블로 둘지 정적 파일로 둘지는 구현 시 정한다. 모든 엔터티를 별도 테이블로 만드는 것을 필수로 해석하지 않는다.
- 기준색 ID는 번역 이름·표시 순서와 독립적이어야 한다. 기존 ID를 다른 색에 재사용하지 않아 기록·Colors 그룹·백업 복원에서 색의 의미가 달라지지 않게 한다. 기준색 목록 버전과 미지원 ID의 검증 방식은 백업 형식에 포함한다.

### 영구 저장과 실패 처리 — 구현 시 구체화할 계약

FR-003의 재실행 복원·실패 시 재시도를 위해 다음을 구현 설계와 검증에 포함한다. 구체적인 파일 API·트랜잭션 코드는 미정이다.

- **Q4 확정 계약:** 첫 붙이기가 성공하면 영구 사진과 첫 색 기록이 존재한다. 이후 붙이기는 같은 `PhotoEntry`에 색 기록을 추가하며 별도 사진 완료를 기다리지 않는다.
- 이미 성공한 붙이기는 화면 이탈로 되돌리지 않는다. 추가 색 저장이 실패해도 기존 사진·샘플을 보존한다.
- 첫 붙이기 전에는 영구 초안을 제공하지 않는다. 이탈 시 폐기 확인, 강제 종료 후 미완성 작업 복구 없음이 확정됐다(Q8). 남은 임시 파일 정리는 앱 소유 파일에 한정하고 갤러리 원본은 삭제하지 않는다.
- 마지막 인덱스를 제거해도 `PhotoEntry`와 영구 사진을 유지한다(Q9). 기존 색·메모·날짜·배치는 각 조작 완료 시 저장한다(Q13). 수정 실패는 성공으로 표시하지 않고 마지막 저장 상태와 재시도 가능한 편집값을 구별한다.

- 촬영 임시 URI만 저장하고 완료로 처리하지 않는다. 앱의 영구 파일 저장 위치와 복사·이동 시점을 정한다.
- 사진 파일과 SQLite 쓰기는 하나의 DB 트랜잭션으로 묶이지 않으므로 실패 시 불완전한 기록·고아 파일을 처리할 순서를 정한다.
- 사진 기록 전체 삭제 시 앱이 소유한 해당 사본·캐시를 자동 정리한다. 마지막 색만 제거할 때는 사본을 유지한다. 중간 실패 후 재시도에서도 다른 기록의 사진이나 갤러리 원본을 삭제하지 않도록 소유 관계와 정리 순서를 검증한다.
- 한 사진의 샘플·배치 저장은 논리적으로 일관되어야 한다. 반복 입력·중간 실패에서 중복이나 다른 색 기록의 유실을 막는다.
- 저장 확정 전 실패하면 현재 선택을 유지하고 재시도를 제공한다. 저장 성공은 실제 보존 완료 뒤에 표시한다.
- 사진 누락·읽기 실패와 기록이 없는 상태를 구분한다. 오류 로그에 사진 내용·개인 메모·불필요한 파일 경로를 남기지 않는다.

### Diary 날짜 계약

- `createdAt`과 화면 분류용 `diaryDate`를 분리한다. 사용자가 날짜를 고쳐도 기록 ID나 생성 시각을 새로 만들지 않는다(Q12).
- 촬영 사진은 촬영일, 가져온 사진은 읽을 수 있는 유효한 원래 촬영일을 우선한다. 날짜 메타데이터가 없거나 잘못되면 가져온 날짜를 쓴다.
- 최적화 과정에서 메타데이터가 없어질 수 있으므로 필요한 촬영일은 최적화 전에 읽고 `diaryDate` 산정에 사용한다.
- 날짜 변경은 그 사진의 Diary 그룹만 옮기며 색·배치·Colors 관계를 유지한다. 백업에도 수정한 Diary 날짜·메모를 포함한다.
- 원본 메타데이터에 시간대가 없는 경우의 날짜 해석과 기기 시간대 변경 처리는 명시적인 날짜 규약으로 고정해야 한다. 구체 규약은 구현 설계에서 정한다.

### 수동 백업·복원 계약

Q10은 기능 범위를 확정한 것이며 상세 형식은 설계 전이다. [ADR-001](adr/ADR-001-local-backup.md)의 결정에 따라 다음을 구현 계획에 포함한다.

- 백업에는 사진 파일과 사진·색·배치의 관계, 실제 채집색, 선택한 기준색 식별 정보, `diaryDate`·`note`가 포함되어야 한다. 색 기록이 0개인 사진도 제외하지 않는다.
- 사진 입력은 앱의 보관 사본이다. 갤러리에 다시 접근하지 않으며, 복원 파일도 앱 전용 영구 저장 영역에 보관한다. 사본 누락·손상은 백업 실패로 안내하고 완료로 처리하지 않는다. 갤러리 재연결·부분 백업은 채택하지 않는다.
- 내보내기 도중 기록 수정으로 사진·DB 내용이 어긋나지 않도록 일관된 상태를 읽는다.
- 앱 내부의 절대 URI를 그대로 복원 경로로 사용하지 않는다. 파일 형식 버전, 참조 무결성, 지원 색 데이터·앱 버전의 호환성을 검사하고 현재 설치의 저장 경로에 맞춘다.
- 가져오는 파일은 신뢰 경계다. 자료형·필수 필드·식별자·파일 존재·크기와 경로를 검증하고 앱 저장 영역 밖의 경로에 쓰지 않는다. 압축 형식을 선택한다면 해제 후 크기도 제한한다.
- 검증·공간 확보가 끝나기 전 기존 기록을 파괴하지 않는다. 파일/DB 반영 실패와 취소 시 이전 Book을 보존하도록 복원 단계를 설계한다.
- **Q14 병합 계약:** `PhotoEntry.id`를 기준으로 새 사진 기록만 추가한다. 같은 ID가 현재 기기에 있으면 해당 사진과 그 하위 색·배치·메모 전체를 건너뛰며, 일부 하위 데이터만 섞지 않는다.
- ID를 복원 때마다 재발급하지 않아 동일 백업의 반복 복원을 중복으로 처리할 수 있어야 한다. 다른 사진에서 하위 ID가 충돌하는 등의 잘못된 관계는 기존 데이터에 덮어쓰지 않고 유효성 오류로 처리한다.
- 삭제 기록의 tombstone을 동기화하지 않는다. 현재 없는 사진이 백업에 있으면 새 기록으로 다시 가져올 수 있다. 추가/건너뜀 건수를 결과에 표시한다.
- 언어 설정은 기기별로 유지하고 복원하지 않는다. 앱에서 제공하는 읽기 전용 Ideas 목록도 사용자 백업 대상에서 제외한다. 선택한 기준색의 식별·호환성 정보는 기록 복원을 위해 포함한다.
- 파일 형식·용량·버전 한계는 후속 기술 설계 항목이다.

## 5. 색 분석 계약

### 처리 범위

1. 촬영을 완료한다.
2. 가져오거나 촬영한 사진을 방향이 반영된 모바일 감상용 사본으로 최적화한 뒤 표시하고 사용자가 위치를 누른다(Q17).
3. 화면 좌표를 이미지 좌표로 변환한다.
4. 선택점 주변의 작은 영역을 crop/resize하고, 별도 픽셀 디코드 단계를 거쳐 대표색을 계산한다.
5. 센서 노이즈, JPEG artifact, highlight, edge pixel 영향을 줄이기 위해 단일 픽셀보다 영역 평균 또는 robust average를 우선 검토한다.
6. 색 후보를 추천하고 사용자가 선택한다.

### 권장 변환 방향

```text
sRGB 입력
  → sRGB linearization
  → XYZ
  → CIELAB
  → Delta E로 후보 비교
```

원본은 단순 RGB Euclidean distance를 피하고 이 경로를 권장한다. 샘플과 기준색에 같은 색공간 규약을 적용해야 한다.

다음은 원본에서 확정되지 않았다.

- **픽셀 디코드 수단**: 실제 이미지에서 픽셀을 읽는 라이브러리·API는 구현 시 Expo SDK 57 호환성을 확인한다.
- **Delta E 방식**: Delta E 76, 94, 2000 등 구체 방식은 구현 전에 결정한다.
- **색공간 기준값**: XYZ 기준 백색점, 입력 이미지 색 프로파일, 반올림 규칙은 구현 전에 확인한다.
- **좌표 규약**: `sourceX/sourceY`는 보관 사본의 픽셀 좌표인지 정규화 좌표인지, 화면-이미지 변환 시 회전·crop·letterbox를 어떻게 처리할지 결정한다.
- **영역 크기와 대표값**: 샘플 영역 크기, 평균·중앙값·trimmed 평균 등 계산법은 실기기 검증으로 결정한다.

**Q17 이미지 계약:** 화면·샘플링·재편집·백업의 기준은 동일한 최적화 사본이다. 해당 사본은 첫 붙이기까지 임시 입력이고 첫 저장에 영구 보관한다. 첫 샘플을 만든 뒤 보관용 사진을 다시 다른 해상도·색공간으로 바꿔 좌표와 색의 기준을 어긋나게 하지 않는다. 필요 시 별도 표시용 썸네일을 만들 수 있지만 기준 이미지를 대체하지 않는다. 해상도·압축률·형식·색공간 정규화는 두 플랫폼에서 화질·메모리·색 일치성을 확인해 결정한다.

### SDK 57 조사 결과 — 2026-09-07

- Camera 사진 URI는 네이티브에서 임시 파일이다. `base64` 반환값도 인코딩된 JPEG 데이터이며 RGB(A) 배열이 아니다. 사진을 오래 보존하려면 영구 복사가 필요하다. [Camera 공식 문서](https://docs.expo.dev/versions/v57.0.0/sdk/camera/)
- ImageManipulator는 좌표 기반 crop/resize를 제공하고 `saveAsync` 결과를 cache directory에 저장한다. 파일 변환과 실제 픽셀 읽기는 별개다. [ImageManipulator 공식 문서](https://docs.expo.dev/versions/v57.0.0/sdk/imagemanipulator/)
- 설치된 FileSystem의 `File.bytes()`는 파일 바이트를 읽고 `File.copy()`는 복사한다. `Paths.document`는 캐시 정리와 구별되는 보존 경로다. 인코딩된 이미지 바이트를 읽는 것만으로 색 배열이 만들어지지는 않는다. 확인한 설치 소스: `node_modules/expo-file-system/src/Paths.ts`, `node_modules/expo-file-system/src/internal/NativeFileSystem.types.ts` (의존성 설치 후 열람 가능).
- 조사한 Camera·ImageManipulator·Image의 공개 API 범위에서는 raw 픽셀값을 직접 반환하는 수단을 확인하지 못했다. **별도 디코더 선정과 iOS·Android 실기기 검증이 남아 있다.** Expo Go 사용 가능 여부도 디코더 선정 전에는 확정하지 않는다.

따라서 핵심 순서는 `촬영/가져오기 → 최적화 사본 → 작은 영역 픽셀 디코드 → 색 추천·사용자 선택 → 붙이기 → 동일 사본의 영구 보관·색 기록 저장`이다. 후보 디코더 호환성·방향/좌표·파일/DB 실패 처리를 실제 실행했다는 뜻은 아니다.

## 6. 색 레퍼런스 데이터

- 앱 내부에 사용자 추천용 자체 색 목록을 둔다.
- 초기 규모는 **약 100~300색**을 권장한다.
- 각 색은 최소한 `name`, `hex`를 가지며 후보 비교에 필요한 `lab`, `family`, `order`를 포함하는 모델을 사용한다.
- 특정 상용 색상 시스템의 이름·데이터를 그대로 무단 복제하지 않는다.
- 추천 결과는 하나로 고정하지 않고 여러 후보를 제공한다. 사용자가 색 의미에 맞는 항목을 선택한다.

## 7. API / 인증 / 보안

### API 계약

외부 HTTP API와 서버가 없다. 따라서 엔드포인트, 요청·응답 JSON, HTTP 오류 코드를 만들지 않는다. 앱 내부 처리는 로컬 함수와 SQLite 계약으로 정의한다.

### 인증·개인정보

- 인증 방식: 없음
- 권한 모델: 사용자 기기의 로컬 데이터 접근 권한만 사용
- 비밀정보 관리: 서버 키·API 키를 두지 않음
- 사진: 외부 서버·AI API로 전송하지 않음
- 위치정보: 필수로 수집·저장하지 않음
- 권한 거부·파일 접근 실패 시 데이터 손실 없이 사용자에게 텍스트로 안내한다.

## 8. 상태 관리·성능·접근성

- 앱의 최초 라우트는 Book이다(Q16). 빈 Book에서 촬영/갤러리로 진입할 수 있고, 기존 기록에서는 다시 색을 붙일 수 있다. 라우트 파일명은 기존 Expo Router 구조에 맞춰 구현 시 정한다.
- **Q6 언어 계약:** 기본은 시스템 언어, 명시적 앱 설정은 한국어 또는 영어다. 앱에서 선택한 언어를 시스템 언어보다 우선하고, 자동 모드에서 지원 외 언어는 영어로 표시한다.
- 색 이름과 Ideas를 포함한 UI 문자열은 한국어·영어로 제공한다. 색의 정체성과 저장 관계는 번역 문자열과 분리한다. 번역 관리 라이브러리·설정 저장 위치는 구현 시 최소 구성으로 정한다.
- 저장 전 화면 상태는 React의 기존 구조를 우선 활용하고, 전역 상태 라이브러리는 필요성이 확인될 때 결정한다.
- 목표 저장소는 SQLite이며 원격 동기화는 없다. 사진 미리보기 등 로컬 캐시 정책은 미정이다.
- 전체 해상도 이미지를 JavaScript에서 처리하지 않고 작은 crop/resize 후 분석하는 방향을 우선 검토한다.
- 촬영 후 색 분석은 체감상 즉시 또는 매우 짧게 완료되어야 한다.
- 픽셀 디코드·색 변환이 UI thread를 막지 않도록 처리 방식과 입력 크기를 실기기에서 검증한다.
- V1에 실시간 frame processor를 추가하지 않는다.
- 색만으로 상태나 오류를 전달하지 않는다. 색 이름·텍스트를 함께 제공한다.
- 충분한 contrast와 터치 가능한 조작 영역을 확보한다.
- 선택·저장·삭제 결과는 색 외 텍스트나 접근성 라벨로 전달한다.

## 10. 테스트·개발·배포 상태

- 현재 확인된 검사 명령: `npm run lint` (`package.json`에 정의됨)
- `npx tsc --noEmit`으로 TypeScript 검사를 수행할 수 있다. 이번 문서 이관에서는 실행하지 않았다.
- `lint` 스크립트는 있으나 ESLint 설정 파일과 직접 의존성은 없다. 검사 구성과 실행 결과는 별도 확인이 필요하며 스크립트 존재를 통과 증거로 삼지 않는다.
- 테스트 스크립트·테스트 러너·`eas.json`은 현재 없다. 자동 테스트·스토어 빌드가 준비됐다고 간주하지 않는다.
- 현재 저장소에는 카메라, 색 분석, SQLite 기능 구현 및 해당 테스트가 없다.
- 구현 시 최소 검증 대상은 화면 좌표 변환, 작은 영역 샘플링, 색 변환·후보 정렬, 한 사진 다중 샘플 저장, 로컬 사진 경로 복원이다.
- 추가 검증 대상은 갤러리 입력, 초안 없는 이탈, 마지막 색 제거 후 사진 유지, 기준색별 Colors 그룹, 백업/복원 성공·손상·취소·중간 실패다.
- 저장 후 갤러리 원본 삭제·보정·권한 철회와 앱 재실행에도 보관 사본·색 기록이 유지되는지, 사진 기록 삭제 시 사본·캐시가 자동 정리되는지 확인한다.
- 개발 실행 명령은 `npm run start`, 플랫폼별 실행은 `npm run ios`, `npm run android`, 웹은 `npm run web`이다.
- 첫 버전의 목표는 스토어 정식 출시 V1이다(Q1). iOS·Android에서 한국어·영어를 제공한다(Q2). 수동 백업·복원은 V1 범위다(Q10, 모두 2026-09-07 확정). 빌드·배포 방식, 마이그레이션·롤백 절차와 백업 파일의 구체 형식은 미정이다.
- 출시 검증은 iOS·Android의 핵심 흐름과 한국어·영어 문구·레이아웃·접근성 이름을 포함한다. 구체적인 OS 최소 버전과 테스트 기기는 아직 결정하지 않았다.
- V1은 무료·광고·인앱결제 없음이다(Q15). 결제·광고 SDK와 관련 서버를 추가하지 않는다.
- `app.json`에는 EAS 프로젝트 연결 정보, 세로 방향, 자동 테마, `chromanote` scheme, 웹 static 출력, typed routes·React Compiler 설정이 있다. EAS 연결 정보만으로 배포 완료를 판단하지 않는다.

## 구현 전 확인이 필요한 미정 설계

1. 실제 픽셀 디코드 수단과 Expo SDK 57 호환 패키지
2. Delta E 방식과 CIELAB 기준 백색점
3. SQLite 열 자료형·날짜 저장 형식·기본키 생성 방식
4. 화면 좌표와 최적화된 보관 사본 좌표의 규약, 회전·crop 처리
5. 샘플 영역 크기·대표값 계산법과 UI thread 영향
6. 확정된 저장/초안/삭제 경계 안에서 영구 사진 경로, 기존 기록 수정과 파일/DB 정리의 일관성
7. 기준 색과 Ideas의 보관 방식, Colors의 무채색 정렬, Diary 날짜·메타데이터의 시간대 규약

9. 보관 사본의 해상도·압축률·형식·색공간 정규화와 실기기 화질/메모리 기준
