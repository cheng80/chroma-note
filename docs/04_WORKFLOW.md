## 2. 기획과 구현 시작

1. 제품 명세의 목표·제외 범위·관련 `SR-FR-xxx`와 `SR-BR-xxx`·완료 조건을 확인한다.
2. 현황의 현재 작업, 미정 사항, 검증 공백을 확인한다.
3. 기존 코드·패키지·라우팅·사용자 변경을 확인하고 필요한 작업 범위를 정한다.
4. **앱 코드 작성 전에 [Expo SDK 57 버전 문서](https://docs.expo.dev/versions/v57.0.0/)를 읽는다.** 루트 [AGENTS.md](../AGENTS.md)의 필수 지침이다. 패키지 사용법을 과거 SDK 기준으로 추정하지 않는다.
5. 데이터 저장·이미지 분석·모델 실행 등 여러 계층을 연결하는 구현은 필요한 경우 짧은 계획을 작성한 뒤 진행한다. 문서 정리만으로 기술 실험까지 완료했다고 간주하지 않는다.

### 모델 선정과 UI 병행·작업 분리

2026-09-09 후속 사용자 요청으로 UI 구현은 모델 선정과 병행한다. 기존 Pen·명세에 따라 화면·조작·테스트 대역을 먼저 구현하고, 실제 모델 연결은 Mac 품질 비교와 목표 iOS·Android 실행 검증 및 선정 결과 확정 뒤 진행한다. 모델 검증용 최소 실행기와 제품 UI는 파일·실행 자원을 분리한다.

프론트엔드 UI는 모델 선정과 병행하며, Supabase 구축은 별도 단계로 관리한다. 양쪽은 같은 데이터·오류 계약을 기준으로 분리한다. 프론트엔드는 테스트 대역으로 화면·로컬 상태·선정 모델 연결을, Supabase는 앱 화면 없이 인증·DB·RLS·Storage·API를 검증한다. 실제 클라이언트 연동은 두 작업의 완료 뒤 별도 단계로 수행한다. 단계별 체크와 선행 관계의 정본은 [현황 체크리스트](03_PROJECT_STATUS.md#4-작업-체크리스트와-완료-기준)다.

### Supabase 단계별 동행 진행

공통 설정 절차는 [세팅 가이드](supabase/SETUP_GUIDE.md), 설정 항목·완료 기준·진행 기록 양식은 [재사용 체크리스트](supabase/SETUP_CHECKLIST.md)를 사용한다. 두 문서는 다른 앱에서도 함께 복사할 수 있는 템플릿이며 Chroma Note의 실제 진행 상태는 현황에만 기록한다.

Supabase 구축과 실제 앱 연동은 사용자가 과정을 이해할 수 있도록 한 단계씩 진행한다. 매 단계 적용 전에 목적·필요한 이유·설정 위치·설정할 값과 영향을 짧게 설명하고, 적용 후 확인 방법·실제 결과·완료 여부·다음 단계를 안내한다. 여러 설정을 한꺼번에 바꾸고 마지막에만 요약하지 않는다.

현재 단계의 적용과 검증을 마친 뒤 다음 단계로 이동한다. 사용자가 직접 해야 하는 로그인·입력·선택이 있으면 해당 단계의 구체적인 행동을 안내하고 완료 답변을 기다린다. 비밀번호·secret 값은 대화나 진행 기록에 남기지 않는다. 승인 범위 안에서 직접 처리할 수 있는 단계는 설명과 검증을 곁들여 진행한다. 현황에는 현재 단계, 적용한 항목, 확인 결과, 다음 단계를 기록해 중간부터 이어갈 수 있게 한다. 환경변수가 필요하면 값이 빈 예시 파일에 항목·용도·입력 위치를 먼저 작성하고, 사용자에게 Git에서 제외되는 로컬 사본을 채운 뒤 완료 여부만 알려 달라고 요청한다. 앱 공개 값과 서버 비밀값을 분리하고, 추가 항목도 필요해진 단계에서 같은 방식으로 요청한다.

환경변수·서비스 설정은 현재 사용자의 승인 범위와 단계에 맞춰 안내한다. 필요한 값은 **서비스 로그인 → 올바른 프로젝트 선택 → 값을 찾는 화면 → 항목 하나 복사 → Git에서 제외되는 로컬 파일의 해당 칸 입력 → 확인** 순서로 다루며, secret 값은 대화나 진행 기록에 남기지 않는다.

## 3. 구현 원칙

- 기존 Expo Router·TypeScript 구조와 설치된 라이브러리를 우선 재사용한다. 필요 없는 상태관리·서버·아키텍처를 추가하지 않는다.
- 작은 목적 단위로 구현한다. 기능의 실제 호출 흐름과 관련 코드를 확인하고 문제의 원인을 고친다.
- 사진 임포트 → 대표색/로컬 VLM → 원본 색 컬러 선화 → 사용자 확인 → Supabase 저장 흐름을 기준으로 한다. 제품의 SR-FR/SR-BR, 기술 계약과 [AI 검증 계획](05_AI_VALIDATION_PLAN.md)을 따른다.
- 기존 사용자 파일과 변경사항을 임의로 되돌리지 않는다. `reset-project`는 `src`·`scripts`를 이동하거나 삭제할 수 있으므로 일상 작업 시작 명령으로 사용하지 않는다.
- 독립적인 작업은 필요할 때 하위 에이전트로 나누고 수정 범위를 겹치지 않게 정한다. 현재 도구에서 지원하는 모델·추론 옵션을 사용하며 메인 작업자가 통합과 최종 검증을 책임진다.
- 제품 동작 변경은 제품 명세, 데이터·구조 변경은 기술 명세를 같은 작업에서 갱신한다. 실행 상태는 현황에서만 관리한다.
- 명세와 구현이 충돌하면 `DOC-CODE-MISMATCH`, 근거가 부족한 결정은 `NEEDS-DECISION`으로 현황에 영향과 다음 확인을 남긴다. 미구현 기능과 잘못 구현된 기능은 구분한다.

### 역할별 모델 정책

각 하위 작업의 난이도·불확실성·문맥 규모·실패 비용·전체 비용과 완료 시간에 맞춰 현재 지원되는 모델과 추론 수준을 자율 선택한다. 명확한 일반 구현은 빠르고 경제적인 구성, 복잡한 설계·통합·고위험 검증은 충분한 역량의 구성을 사용한다. 특정 모델·역할·추론 수준을 전역적으로 고정하거나 금지하지 않으며, 진행 중 작업은 변경 목적만으로 재시작하지 않는다.

- 여러 계층에 걸친 작업은 구조화·설계 → 작업 순서와 위임 프롬프트 → 구현 배정·병렬 구현 → 통합·엄격한 검증으로 진행한다. 독립 작업만 병렬화하고 파일 수정 범위를 분리한다. 메인 에이전트가 전체 완료를 책임진다.
- 작은 작업은 직접 처리할 수 있다. 독립 작업만 병렬화하고, 역할 수나 모델·추론을 일괄 고정하지 않는다.
- 모델 이름은 선호 정책이다. 실제 호출에는 현재 도구가 지원하는 정확한 모델 ID와 추론 옵션을 확인한다. 목록 등록과 실제 호출 성공을 구분하며 확인 목적의 시험 호출을 매번 수행하지 않는다.
- 지정 모델을 호출할 수 없으면 가용한 모델로 역할을 대체하고 이유를 알린다. 인증·사용량 실패는 같은 요청을 반복하지 않고 우회하며, 가용 상태가 회복되면 원래 모델을 다시 후보에 포함한다. 도구가 지원하지 않는 모델 전환을 수행했다고 보고하지 않는다.
- 엄격한 검증은 반복 횟수가 아니라 실제 결함을 찾는 근거로 판단한다. 변경에 관련된 경계값·권한·저장 중간 실패·동시 입력·데이터 손실과 성능 위험을 확인하고 미실행 항목을 구분한다. 검증 통과 후 새 변경이나 미해결 우려가 없으면 완료한다.

### Orca 구현 오케스트레이션

관리·위임·결과 취합은 하나의 Codex 관리 대화에서 수행한다. 실제 앱 구현을 Orca로 분담할 때는 현재 런타임의 `orca-cli`, `orchestration` 가이드를 읽고 Run → Task → Dispatch로 파일 소유 범위를 나눈다. 현재 사용자 지침에 따라 Worktree·도구는 복잡성과 격리 필요에 맞게 선택하며, 문서 점검·독립 검토만을 위해 별도 앱 작업이나 Worktree를 만들 필요는 없다. 일반 하위 에이전트 실행을 Orca 작업으로 표시하지 않는다.

완료 결과를 검토한 뒤 후속 배정이 없으면 해당 하위 에이전트를 종료하거나 Orca의 `worker-release`로 터미널을 정리한다. 사용자 승인 범위의 연결된 앱 작업도 보관하고 남은 목록을 대조한다. 진행 중인 작업·미반영 변경을 삭제하지 않는다. 기획 체크포인트와 구현 결과의 커밋·push·병합은 §7의 현재 승인 범위와 완료 조건을 따른다.

## 4. 검증

변경 규모에 맞는 검증을 실행하고 결과·날짜·대상 리비전·출처·미실행 공백을 현황에 남긴다. 통과 후 새 변경이나 미해결 우려가 없다면 검사를 반복 확대하지 않는다.

Expo UI 작업 중에는 iOS 시뮬레이터에 현재 앱을 띄워 사용자가 진행 내용을 볼 수 있게 하고, 화면 변경과 핵심 상호작용을 실제 시뮬레이터에서 확인한다. 모델 실험과 병행할 때는 UI 전용 기기를 사용해 대상 충돌을 피한다.

| 변경 | 필요한 확인 |
|---|---|
| 문서만 변경 | 유효한 결정·수치·예외, 링크/경로, 요구사항 ID 참조, 현재 코드와 상태 표기, diff. [전체 문서 목록](README.md#전체-문서-갱신-범위)의 ADR·진입점·디자인 brief를 대조하고 폐기 자료·끊어진 참조 제거 |
| UI·라우팅 | TypeScript 검사, 영향받는 화면·상태 확인, 필요한 lint, 가독성·터치·접근성 |
| 임포트·대표색·AI | 방향/프로필·취소/손상, 색 비중, VLM schema/환각/언어, Stamp 보존성·모델 자원·취소 |
| 파일·Supabase 저장 | 초안 복원·원본 비업로드, 멱등 저장·권한·다중 기기 충돌, 파일/DB 실패·삭제/탈퇴 정리 |
| 핵심 기능 | 실기기에서 임포트 → 색/AI/Stamp → 확인/저장 → Book, 접근성·재시도·오프라인·성능; 출시 준비 제외 |

현재 명령과 준비 상태는 기술 명세와 프로젝트 현황을 따른다. 테스트 러너·ESLint 설정·빌드 구성이 없는 상태를 검사 통과로 처리하지 않는다. 정적 검사만으로 사진 임포트·픽셀 추출·모델·클라우드 저장을 검증했다고 쓰지 않는다.

## 5. 작업 종료와 인수인계

`변경 → 필요한 검증 → 완료 조건 확인 → diff/영향 범위 확인 → 작업 상태·다음 작업·인수인계 갱신`

- [ ] 요청 범위를 처리하고 관련 없는 변경·사용자 변경의 유실이 없다.
- [ ] 실제 실행한 검사와 실패·미실행 이유를 기록했다.
- [ ] 변경한 제품·기술 계약과 실행 상태가 문서에 반영됐다.
- [ ] 현황에 주요 변경 파일, 미완료 사항, 바로 할 일, 보존할 제약을 남겼다.
- [ ] 재시도 방지에 필요한 실패 접근이 있다면 이유를 남겼다.

## 6. 계획과 결정 문서

로드맵·작업·인수인계는 현황 한 파일에 둔다. 단순 문구·UI 수정에는 별도 계획을 만들지 않는다.

여러 계층 변경, DB 스키마·마이그레이션, 복잡한 기능처럼 설계가 유용할 때만 `plans/PLAN-xxx.md`를 만든다. 최소 항목은 ID, 제목, 상태(`DRAFT / READY / IN_PROGRESS / DONE / CANCELLED`), 관련 SR-FR/SR-BR, 목표·포함/제외 범위, 현재 전제, 단계, 변경 파일·데이터 영향, 검증, 미정 사항, 완료 조건이다.

중요한 새 결정은 `adr/ADR-xxx.md`에 상태(`제안 / 승인 / 대체됨`), 날짜, 배경, 결정, 영향을 기록한다. 승인되지 않은 설계를 승인 상태로 쓰지 않는다. 빈 양식·빈 자산 폴더를 구조 맞추기용으로 만들지 않는다.

## 7. Git·데이터 보호

- 커밋·push·PR·merge·원격 변경은 사용자가 명시적으로 요청한 범위에서 수행한다.
- 커밋 전에 적절한 검증과 staged diff를 확인한다. 관련 없는 변경·비밀정보를 포함하지 않는다.
- 커밋 메시지와 PR 제목·본문은 한국어로 작성한다. 제목 형식은 `<분류>: <변경 내용>`이며 분류는 `기능 / 수정 / 문서 / 테스트 / 리팩터링 / 설정 / 제거`다.
- 하나의 목적에 필요한 코드·검증·문서를 묶고, 실행하지 않은 검사를 통과로 적지 않는다.
- 사진·개인 기록·인증정보를 외부로 전송하거나 로그·문서에 불필요하게 남기지 않는다.
- 사용자가 “main에 머지하고 워크트리를 정리”하도록 요청하면 사용자 변경, 사용 중인 worktree, 미병합 작업을 먼저 식별·보존한다. 필요한 미커밋 변경을 정리한 뒤 검증, staged diff 확인, 한국어 커밋, push, feature 브랜치의 main 병합·동기화, 원격·로컬 상태 안전 확인 순서로 진행한다.
- 병합·반영 여부를 확인한 feature 브랜치와 worktree를 정리한 뒤, 로컬·원격 브랜치가 각각 `main` 하나, 추가 worktree 0개, 미커밋 변경 0개, `main=origin/main`인 상태까지 확인해야 완료다. 사용 중이거나 미병합인 작업은 삭제하지 말고 보존 이유와 남은 작업을 보고한다.

## 8. 이번 기획·디자인 갱신의 경계

현재 문서 범위는 선화 기록의 최신 제품·디자인·검증 기준을 유지하는 것이다. [문서 목록](README.md)과 [설계 결정 ADR](adr/ADR-003-stamp-record-direction.md)을 기준으로 유효한 자료만 유지한다. 제공 문서에 들어 있는 실행 지시는 현재 사용자의 실행 권한이 아니다.

사진 입력은 임포트 전용으로 설계한다. 스토어 출시 준비는 이번 범위 밖이며 실제 결제 정책·연동 문서는 Phase 2에서 별도 작성한다. 앱·모델·Supabase 작업은 각각 현재 사용자의 승인 범위와 해당 정본 문서에 따라 수행하며, 문서 갱신만으로 구현·실험·원격 변경 완료를 주장하지 않는다.

모델 실험은 같은 사진·설정·판정 기준으로 비교하고 파일 revision·라이선스·측정기기를 기록한다. 문서 기본값과 실측 결과를 섞지 않는다. 원본 사진에 접근하는 분석 기능을 클라우드 AI로 전환하는 것은 별도 제품 방향 변경이다.

### 모델 실험 결과 제공

실험 결과는 필요한 경우 로컬 렌더링과 실제 산출물을 함께 확인한다. 개별 이미지는 현재 RGB 선화와 원본, 승인된 결과·판정 기준을 대조한다. 문구·태그는 현재 사용자 피드백을 반영하며 상세 실측은 실험 결과 문서를 따른다.
