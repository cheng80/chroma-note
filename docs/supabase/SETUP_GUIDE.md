# Supabase 단계별 세팅 가이드 — 다른 앱에서도 재사용하기

공식 문서 확인일: **2026-09-09**. [체크리스트](SETUP_CHECKLIST.md)에 앱별 값을 채운 뒤 이 가이드의 같은 단계 ID를 따라간다. Hosted Supabase의 개발 환경 구축부터 실제 연동까지 설명하며, 실행 스크립트나 이미 적용된 설정 보고서가 아니다.

## 읽는 방법

한 단계 안에서도 **목적 설명 → 설정 항목 하나 확인 → 적용 → 실제 결과 확인 → 다음 항목** 순서로 진행한다. 여러 설정을 몰아서 적용하지 않는다. 설명은 사용자가 이해할 수 있는 말로 하고, 화면 이름·파일·필드명은 원문을 함께 보여 준다. 실패하면 해당 항목의 원인을 해결한 뒤 진행한다. 사용자가 직접 로그인·입력해야 한다면 구체적인 행동을 안내하고 완료를 기다린다.

화면 메뉴와 기본값은 변경될 수 있다. 아래 위치는 찾을 기능의 이름이며, 실제 작업 때 대상 프로젝트의 화면·요금제·CLI/SDK 버전과 공식 문서를 다시 확인한다. 비용이 드는 선택은 해당 단계에서 설명하고 기존 승인 범위를 따른다. 문서 복사가 계정 생성·과금·원격 변경·배포 권한은 아니다.

| 용어 | 이 가이드에서의 뜻 |
|---|---|
| Auth | 사용자가 누구인지 확인하는 로그인·세션 기능 |
| Database / table / row | 데이터베이스 / 같은 종류의 데이터 묶음 / 기록 한 건 |
| grants / RLS | 어떤 종류의 작업을 허용하는지 / 그중 어느 사용자의 행을 허용하는지 |
| Storage / bucket | 파일 보관 기능 / 공개 범위와 제한을 정하는 파일 묶음 |
| migration | DB 구조·정책 변경을 순서대로 다시 적용할 수 있는 기록 |
| Edge Function / RPC | 서버에서 실행하는 처리 / API로 호출하는 DB 함수 |
| Cron / Realtime | 정기 작업 / 변경 등을 실시간으로 전달하는 기능 |

<a id="sb-00"></a>
## SB-00 — 이 앱에서 필요한 것부터 정하기

**목적:** 앱마다 다른 인증·데이터·공개 범위를 먼저 정한다.

1. 체크리스트의 앱 이름·플랫폼·선행 조건·담당자를 채운다. AI 모델 검증 같은 선행 조건이 있다면 완료 여부를 확인한다.
2. 데이터 목록을 적는다. 각 데이터에 소유자, 읽는 사람, 수정하는 사람, 필수값, 보존·삭제 시점을 붙인다.
3. 아래 권한 표를 앱에 맞게 채운다. 개인 기록 예시를 팀 협업 앱에 그대로 적용하지 않는다.
4. 파일·서버 처리·정기 작업·실시간 기능을 선택한다. 필요 없는 기능은 설정하지 않고 이유를 남긴다.

| 데이터 / 작업 | 미인증 | 소유자 A | 타 사용자 B | 서버 처리 |
|---|---|---|---|---|
| 개인 기록 조회 | 거부 | 자기 것만 | 거부 | 필요한 범위만 |
| 개인 기록 생성·수정·삭제 | 거부 | 앱의 저장 계약에 따라 허용 | 거부 | 필요한 검증 후 처리 |
| 공개·팀 데이터 | 앱별 작성 | 앱별 작성 | 팀 역할·공개 정책에 따라 작성 | 앱별 작성 |

**확인:** 핵심 데이터마다 권한과 수명이 설명되고 미정 항목이 드러나면 준비 완료다. 실제 DB는 아직 만들지 않는다.

<a id="sb-01"></a>
## SB-01 — 프로젝트와 개발 환경 준비

**목적:** 어느 앱·어느 환경을 설정하는지 확실히 구분한다. **위치:** Supabase Dashboard의 조직·프로젝트 생성 화면, 프로젝트 설정, 필요하면 로컬 개발 도구.

1. 로그인 후 사용할 조직과 기존 프로젝트 유무를 확인한다. 새로 만들 경우 이름·리전·요금제·DB 비밀번호의 의미를 하나씩 설명한다. 이름은 `앱이름-dev`처럼 환경을 알아볼 수 있게 정할 수 있다.
2. 실제 사용자 지역과 필요한 기능·비용을 보고 값을 선택한다. 비밀번호는 비밀 관리 도구에 보관한다.
3. 프로젝트가 준비되면 project ref·환경·리전을 기록한다. 웹사이트 주소와 Supabase 프로젝트 URL을 구분한다.
4. 로컬 환경이 필요하면 현재 CLI 설치 안내와 `--help`를 확인해 초기화·시작한다. 기존 프로젝트는 원격 구조를 먼저 가져와 기준을 맞추며 빈 앱 기준 초기화를 덮어씌우지 않는다.

**확인:** 대상 환경이 식별되고 개발 서비스에 연결된다. **막히면:** 권한·리전·조직의 사용량·로컬 실행 조건을 확인한다. 다른 프로젝트를 임의로 대신 사용하지 않는다. 환경 분리 방식은 별도 프로젝트·지원되는 브랜치·로컬 환경 중 필요와 요금제에 맞춰 선택한다. [공식 환경 관리](https://supabase.com/docs/guides/deployment/managing-environments), [로컬 개발](https://supabase.com/docs/guides/local-development/overview)

<a id="sb-02"></a>
## SB-02 — 앱과 서버의 연결 정보 분리

**목적:** 앱 연결에 필요한 값과 관리자 권한을 구분한다. **위치:** 프로젝트의 `Connect`, `Settings > API Keys`, 앱 환경설정과 서버 비밀 관리.

1. 프로젝트 URL과 publishable key를 앱 설정에 연결한다. 공개 환경변수의 이름은 사용하는 프레임워크 규칙을 따른다.
2. 서버 관리 권한이 실제로 필요한 처리만 secret을 서버 비밀 관리에 보관한다. 앱 번들·공개 접두사의 환경변수·대화·Git에는 넣지 않는다. DB 비밀번호·연결 문자열도 앱에 넣지 않는다.
3. 기존 앱의 `anon`/`service_role`은 legacy 키인지 확인한다. 키 종류를 바꿀 때 이미 사용 중인 연결까지 영향 범위를 확인한다.
4. 키는 호출하는 앱을, 로그인 세션은 사용자를 식별한다. publishable key를 넣었다는 이유로 RLS 검증이 끝난 것은 아니다.

**확인:** 앱에 관리자 권한이 없고, 잘못된 키·프로젝트 연결은 정상 인증과 구분된다. secret으로 성공한 요청은 일반 사용자 권한 테스트가 아니다. **막히면:** 환경변수 로딩·프로젝트 URL·키 종류부터 확인한다. [공식 API 키 안내](https://supabase.com/docs/guides/getting-started/api-keys)

### 환경변수 예시를 채우는 순서

현재 저장소에는 [앱용 예시](../../.env.example)와 [서버용 예시](.env.server.example)를 제공한다. 값은 모두 비워 두었다. `.env.example`을 수정해 실제 값을 저장하지 않고 아래 로컬 사본에 입력한다. 기존 로컬 파일이 있으면 덮어쓰지 말고 빠진 항목만 채운다.

| 예시 파일 | 사용자가 작성할 파일 | 작성 시점 / 필요한 값 |
|---|---|---|
| 저장소 루트 `.env.example` | 저장소 루트 `.env` | 개발 프로젝트가 준비된 SB-02: URL·publishable key |
| 이 폴더 `.env.server.example` | 이 폴더 `.env.server` | 관리자 처리가 필요한 SB-06: 서버 URL·secret key |

1. 해당 단계에 도달했을 때 입력을 요청한다. 안내자는 서비스 로그인·프로젝트 선택부터 함께 확인한 다음, 값을 찾는 메뉴와 정확한 항목 → 복사할 값 → 로컬 파일의 입력 칸을 하나씩 짚는다. 앱 URL을 확인한 뒤 publishable key로 넘어가고, 서버 secret은 필요한 서버 단계에서 안내한다. 사용자가 위치를 이미 안다고 가정하거나 아직 필요 없는 파일 작성을 미리 요구하지 않는다. 사용자는 예시를 로컬 사본으로 복사하고 안내받은 항목의 `=` 뒤에 값을 입력한다.
2. **실제 값을 채팅에 붙이지 말고 “앱 env 작성 완료” 또는 “서버 env 작성 완료”라고 알려 준다.** 안내자는 값 자체를 출력하지 않고 필수 항목 존재·빈 값·키 종류·프로젝트 일치·Git 제외 여부를 확인한다. 연결 검증은 해당 단계의 승인된 환경에서 수행한다.
3. 다른 설정이 추가로 필요해지면 먼저 예시 파일에 항목·용도·입력 위치를 추가하고 사용자에게 그 항목만 요청한다. 미정인 비밀번호·SMTP·OAuth 값을 한꺼번에 요구하지 않는다.
4. SMTP 발신 정보는 Auth의 SMTP 설정, DB 비밀번호는 비밀 관리 도구, 선택한 OAuth 제공자의 secret은 해당 서버/제공자 설정에서 관리한다. 이 값들을 앱 env에 모으지 않는다.

Expo의 `EXPO_PUBLIC_`는 앱에 포함되는 공개 값이다. `.env.local`을 Git에서 제외해도 앱 번들에서 secret을 숨길 수는 없다. 다른 프레임워크에서는 공개 변수 이름을 바꾸고 그 프레임워크의 로딩 규칙을 확인한다. [Expo 환경변수](https://docs.expo.dev/guides/environment-variables/)

서버 예시의 `SERVER_` 이름은 이 템플릿의 별도 서버 설정 이름이며 자동 주입을 뜻하지 않는다. 배포된 Supabase 함수의 기본 환경값이나 현재 SDK 인증 방식과 맞춰 실제 서버 구현 단계에서 연결한다. 로컬 검사 도구가 이 값을 사용하더라도 실제 제품 앱·서버 연결 완료를 뜻하지 않으며 env 작성만으로 연동이 끝나지 않는다.

현재 저장소의 `.gitignore`는 `.env`, `.env.server`, `.env*.local`을 제외한다. 다른 앱으로 옮길 때도 선택한 로컬 사본이 제외되는지 먼저 확인한다. 실제 값은 커밋하지 않고 값이 빈 예시만 공유한다.

<a id="sb-03"></a>
## SB-03 — 인증과 메일 설정

**목적:** 선택한 방식으로 사용자가 로그인하고 앱으로 돌아오게 한다. **위치:** `Authentication`의 로그인 제공자·이메일·URL·SMTP 설정. 세부 명칭은 실제 화면에서 확인한다.

1. 이메일 코드, 링크, 비밀번호, OAuth 중 사용할 방식을 먼저 정하고 가입 허용 여부를 맞춘다. 필요 없는 제공자는 켜지 않는다.
2. 이메일 코드를 쓰면 메일 템플릿에서 숫자 token을 제공하도록 하고 코드 길이·만료·재발송 안내를 실제 설정에 맞춘다. 링크형 메일을 보내면서 앱에는 코드 입력만 요구하지 않는다. [이메일 코드·링크 안내](https://supabase.com/docs/guides/auth/auth-email-passwordless)
3. 메일 템플릿을 수정할 수 있는지 먼저 확인한다. **2026-06-03 이후 새 무료 프로젝트가 기본 SMTP를 사용하면 템플릿 수정이 제한된다.** 기존 프로젝트·유료 요금제·자체 SMTP의 적용 조건은 다르다. 제한에 해당하면 SMTP나 요금제 선택을 먼저 해결하고 인증 완료로 표시하지 않는다. [변경 공지](https://supabase.com/changelog/46599-changes-to-email-template-customisation-on-free-tier)
4. SMTP가 필요하면 제공자·발신 주소/도메인·host·port·보안 방식·자격증명의 의미를 하나씩 확인한다. 제공자에서 요구하는 도메인 인증도 수행한다. 기본 메일 서비스의 수신자·발송 한도를 실제 프로젝트에서 확인하며, 테스트 메일 한 통의 성공을 일반 사용자 발송 가능으로 확대하지 않는다. [SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp)
5. 링크/OAuth는 앱의 실제 callback을 먼저 정한 뒤 `Site URL`과 허용 redirect에 환경별 값을 넣는다. 모바일은 앱 scheme 또는 연결된 HTTPS 경로를 실제 앱에서 검증한다. 코드 입력만 사용하는 흐름에 임의 callback을 추가하지 않는다. [Redirect URL 안내](https://supabase.com/docs/guides/auth/redirect-urls)
6. 테스트 계정으로 정상 인증, 잘못된 코드, 만료, 재발송, 로그아웃을 확인한다. 실제 앱으로의 복귀·재실행 세션 검증은 SB-08에서 마친다.

**확인:** 선택한 인증 방식과 실제 수신 내용이 일치한다. **막히면:** Auth 로그·메일 발송 결과·템플릿 제한·수신 대상·callback을 차례로 확인한다. 비밀번호나 수신 코드를 진행 기록에 남기지 않는다.

<a id="sb-04"></a>
## SB-04 — 테이블과 접근 권한을 함께 만들기

**목적:** 저장할 데이터와 사용자가 접근할 범위를 같은 변경으로 만든다. **위치:** 앱 소유 schema, migration 파일, Table Editor와 정책 화면.

1. SB-00의 데이터 목록을 테이블·필드·자료형·기본값·필수 여부·PK/FK·제약으로 바꾼다. 사용자 프로필이나 팀 테이블도 앱에서 필요할 때만 추가한다. Supabase 관리 schema에 임의 앱 테이블을 만들지 않는다.
2. 변경을 재현할 migration 방식을 정한다. 이 가이드의 기본은 변경마다 migration을 남기는 방식이며, 이미 선언형 schema를 쓰는 앱은 기존 방식을 유지한다. 생성된 SQL은 적용 전에 읽는다.
3. DB API에 노출할 schema·테이블과 최소 grants를 정하고 RLS를 함께 적용한다. 새 프로젝트의 테이블은 자동 노출을 기대하지 않는다. grants는 테이블 작업 권한, RLS는 행 범위이므로 한쪽만 설정하지 않는다. [Data API 변경 공지](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)
4. 개인 데이터의 정책은 실제 인증 UID와 소유자를 비교한다. 수정은 기존 행 접근과 바뀐 행 소유권을 둘 다 검사한다. 사용자가 수정할 수 있는 `user_metadata`를 권한 근거로 쓰지 않는다. [RLS 안내](https://supabase.com/docs/guides/database/postgres/row-level-security)
5. A 로그인 세션으로 A 데이터와 B 데이터를 각각 요청한다. B와 미인증도 같은 작업을 반복한다. 조회가 빈 배열을 반환하는 거부와 쓰기 거부를 구분하고, 영향받은 행까지 확인한다. SQL Editor의 관리자 권한이나 secret key로 대신하지 않는다.
6. 클라이언트 직접 쓰기와 서버 API를 구분한다. 서버만 확정해야 할 상태·경로·버전을 앱에서 수정할 수 없게 한다. view·RPC를 추가했다면 테이블 정책을 우회하는지 별도 검사한다.

**확인:** 권한 표의 허용·거부가 모두 맞고 소유권 이전·타 사용자 접근·서버 상태 우회가 차단된다. **막히면:** 실제 세션 → schema/API 노출 → grants → RLS → 입력 제약 순으로 확인한다. RLS를 끄거나 전체 권한을 열어 해결하지 않는다. [API 보안](https://supabase.com/docs/guides/api/securing-your-api)

<a id="sb-05"></a>
## SB-05 — 파일 보관 설정

**목적:** 파일을 누가 올리고 읽고 지울 수 있는지 정한다. 파일 기능이 없으면 `해당 없음`으로 기록한다. **위치:** `Storage`의 bucket 생성·설정·정책.

1. bucket 이름, private/public, 허용 MIME, 최대 파일 크기를 한 항목씩 정한다. 공개 접근은 실제 공개 자산에만 사용한다. [Bucket 생성](https://supabase.com/docs/guides/storage/buckets/creating-buckets)
2. 앱별 소유권에 맞는 경로를 정한다. 개인 파일이라면 사용자/기록/파일 단위 경로를 사용할 수 있다. 경로 문자열만 믿지 않고 사용자와 관련 DB 기록을 검증한다.
3. 업로드·조회·덮어쓰기·삭제를 따로 허용한다. 새 업로드와 upsert에 필요한 권한은 다르다. 파일 덮어쓰기가 필요하지 않으면 허용하지 않는다. [Storage 권한](https://supabase.com/docs/guides/storage/security/access-control)
4. private 파일을 인증 요청이나 필요한 수명의 signed URL로 읽는다. 만료되는 URL을 영구 파일 ID로 저장하지 않는다. [파일 다운로드](https://supabase.com/docs/guides/storage/serving/downloads)
5. A/B/미인증과 잘못된 경로·파일 크기·포맷으로 검사한다. 업로드 성공뿐 아니라 권한 없는 읽기와 삭제 거부도 확인한다.
6. DB 저장과 파일 저장은 하나의 성공으로 가정하지 않는다. 중간 실패·미참조 파일·DB 삭제 뒤 남는 파일의 정리 순서와 책임을 정한다.

**확인:** 의도한 파일만 접근 가능하고 실패 뒤 데이터가 복구 또는 정리된다. **막히면:** bucket·요청 경로·세션·요청 작업의 정책·파일 제한을 확인한다. 이미지가 안 보인다는 이유로 bucket을 public으로 바꾸지 않는다.

<a id="sb-06"></a>
## SB-06 — 서버 처리와 필요한 부가 기능

**목적:** 관리자 권한과 여러 자원에 걸친 처리를 서버에 둔다. **위치:** `Edge Functions`, DB 함수/RPC, 필요한 작업 스케줄·비밀 관리 설정.

1. 서버 처리 목록을 요청·응답·오류·인증 주체와 함께 정한다. 한 기능씩 구현하고 검증한다. 단순 작업에 불필요한 서버 계층을 추가하지 않는다.
2. 사용자 호출, 정기 작업, 외부 webhook을 구분해 각각 인증한다. publishable/secret key를 사용자 JWT처럼 다루지 않는다. 인증 오류를 없애기 위해 보호를 제거하지 말고 현재 런타임의 공식 호출 방식을 확인한다. [Edge Function 인증](https://supabase.com/docs/guides/functions/auth)
3. 관리자 권한을 쓰는 처리도 검증된 사용자·소유권·허용 필드를 확인한다. `SECURITY DEFINER`가 필요한 함수는 호출 권한·실행 경로·UID 검사를 명시하고 최소화한다.
4. 중복 요청에는 같은 결과를, 오래된 수정에는 충돌을, 부분 실패에는 재시도 가능한 상태를 반환하도록 앱의 계약을 구현한다. 결과를 알 수 없으면 성공으로 표시하지 않는다.
5. 삭제/탈퇴는 파일·DB·사용자·세션의 수명을 함께 처리한다. Auth 사용자 삭제만으로 파일 정리와 기존 토큰 무효화가 끝났다고 가정하지 않는다. [사용자 데이터 관리](https://supabase.com/docs/guides/auth/managing-user-data)
6. Cron·Realtime·확장 등은 선택한 기능에만 추가한다. 실행 주체·주기·재시도·로그를 설명하고 실제 요청으로 확인한다. [Cron](https://supabase.com/docs/guides/cron), [Realtime](https://supabase.com/docs/guides/realtime)

**확인:** 실제 API에서 허용·거부·중복·부분 실패가 의도대로 처리된다. **막히면:** 호출 인증과 함수 내부 권한을 분리해 살핀다. 서버 secret이 있다는 이유로 입력 UID·경로를 신뢰하지 않는다.

<a id="sb-07"></a>
## SB-07 — 앱 없이 서버를 검증하고 다시 만들 수 있게 하기

**목적:** UI 문제와 서버 문제를 분리한다. **위치:** 폐기 가능한 로컬 DB, migration, 개발 프로젝트, 테스트 기록·Advisor.

1. 로컬 migration 전체를 재적용해 테이블·정책·함수가 재현되는지 확인한다. reset은 데이터를 지우므로 대상과 보존 필요를 확인한 폐기용 환경에서만 사용한다. 원격 reset을 일상 재현 절차에 넣지 않는다.
2. migration이 모든 설정을 담는다고 가정하지 않는다. Auth·SMTP·bucket·함수 배포·secret·스케줄의 선언 파일 또는 재설정 순서를 따로 기록한다. 비밀값 자체는 제외한다.
3. 원격 개발 환경 적용 전 대상 project ref와 변경 목록을 확인하고, 적용 후 로컬·원격 migration 상태와 테스트 결과를 비교한다. 실제 사용 중인 DB의 실패를 무작정 초기화해 해결하지 않는다. [Migration 안내](https://supabase.com/docs/guides/local-development/database-migrations)
4. 테스트 계정과 비개인 fixture로 인증·DB·파일·API 권한 검사를 반복한다. Advisor의 관련 문제를 해결하거나 적용하지 않는 이유를 기록한다.
5. 프론트엔드에 환경 식별자, 공개 연결 정보, 데이터/오류 계약, 검증 결과를 전달한다. 관리자 키를 공유 문서로 전달하지 않는다.

**확인:** 서버 독립 테스트가 통과하고 재현 방법이 남는다. 프론트엔드 완료 여부와 별개로 이 단계의 상태를 기록한다.

<a id="sb-08"></a>
## SB-08 — 실제 프론트엔드 연결

**목적:** 검증된 화면과 서버를 순서대로 연결한다. **진입 조건:** 서버 독립 검증과 프론트엔드의 테스트 대역 검증 완료.

1. 앱 플랫폼에 맞는 현재 공식 SDK 가이드를 확인한다. 모바일의 세션 보관·앱 복귀와 웹의 서버/브라우저 인증은 따로 다룬다. 연결 정보는 SB-02의 공개/비밀 구분을 유지한다.
2. 로그인·세션 복원을 먼저 연결하고 실제 사용자의 UID를 확인한다. 사용자 A에서 B로 바뀔 때 로컬 데이터와 진행 요청이 섞이지 않는지도 검사한다.
3. 읽기 → 생성/파일 업로드 → 저장 확정 → 편집 → 삭제 순으로 하나씩 연결한다. 각 단계에서 실제 서버 데이터와 화면 상태가 맞는지 확인한다.
4. 화면의 임시 저장/대기 상태와 서버 확정을 구분한다. 응답 유실·오프라인·세션 만료·중복 요청·충돌·탈퇴를 실제 서비스에서 검사한다.
5. 개인 데이터가 로그·진단 첨부·부적절한 백업에 포함되지 않는지 확인하고, 결과와 남은 미실행 범위를 기록한다.

**확인:** 실제 환경의 정상·실패 흐름이 끝까지 동작한다. **막히면:** 프론트엔드 입력·세션·요청·서버 결과를 순서대로 추적하고 테스트 대역의 성공을 실제 성공으로 계산하지 않는다. [공식 React Native 시작점](https://supabase.com/docs/guides/auth/quickstarts/react-native), [서버 측 인증](https://supabase.com/docs/guides/auth/server-side)

<a id="sb-09"></a>
## SB-09 — 운영 준비를 요청받았을 때

개발 세팅 완료와 운영 배포 완료를 구분한다. 운영 범위가 없다면 `해당 없음`으로 남긴다.

1. 실제 요금제에서 메일·DB·Storage·함수의 한도와 사용량 확인 방법, 장애 알림 담당을 정한다. 가격·한도는 템플릿에 고정하지 않는다.
2. DB와 파일의 백업 범위·보존 기간·복원 절차를 각각 확인한다. **DB 백업은 Storage 파일 자체를 백업하지 않는다.** 복원 가능한 자원을 실제로 구분하고 필요한 파일 복구 방식을 준비한다. [백업 안내](https://supabase.com/docs/guides/platform/backups)
3. 계정 삭제·서버 장애·키 노출 시 조치와 재발 방지를 기록하고, 운영 변경은 해당 배포 범위에서 수행한다.

**확인:** 운영 준비가 실제 검증됐을 때만 완료다. 이 문서를 읽거나 개발 환경을 만든 것만으로 운영 완료로 표시하지 않는다.

## 재사용 전 마지막 점검

두 문서와 필요한 env 예시를 함께 복사하고 체크리스트의 프로젝트 값을 교체한다. 이 저장소의 앱 예시는 루트에, 서버 예시는 가이드 옆에 있으므로 새 저장소에서도 경로를 맞추거나 문서의 링크를 갱신한다. 인증 방식, 개인/팀 권한, 파일 공개 범위, 서버 역할, 운영 범위를 새 앱 기준으로 다시 결정한다. 기존 앱의 테이블·정책·완료 체크를 자동으로 복제하지 않는다. 설정을 시작할 때 [Supabase 변경내역](https://supabase.com/changelog)을 확인하고 영향을 받는 단계의 공식 자료를 다시 읽는다.

검증 범위: 공식 문서 대조와 문서 자체의 링크·구조 검사. 실제 계정·프로젝트·DB·메일·앱 연결을 설정하거나 테스트한 보고서가 아니다.
