# Supabase 세팅 체크리스트 — 재사용 템플릿

문서 기준일: 2026-09-09. **설정 완료 기록이 아닌 빈 템플릿**이다. [세팅 가이드](SETUP_GUIDE.md)와 함께 다른 앱 저장소로 복사해 사용한다. Hosted Supabase 기준이며 로컬 개발은 검증 보조 환경이다.

새 앱에서는 아래 프로젝트 정보를 채우고 모든 체크를 비운 상태에서 시작한다. 단계 ID는 가이드와 같다. `해당 없음`은 적용하지 않는 이유를 기록하며 완료 체크로 대신하지 않는다. 이 템플릿의 단계별 진행 기록을 사용 중인 프로젝트 현황 문서에 옮겨 기록하면 완료 상태를 두 곳에서 관리하지 않아도 된다.

## 프로젝트별로 먼저 채울 값

| 항목 | 이 앱의 값 |
|---|---|
| 앱 이름 / 저장소 / 진행 현황 문서 | 미정 |
| 작업자 / 확인자 / 시작일 | 미정 |
| 앱 구현 전 선행 조건 | 미정 — AI 앱이면 모델 선정 여부 등 |
| 클라이언트 | 미정 — 웹 / iOS / Android / 기타 |
| 조직 / 개발 프로젝트 이름 / project ref | 미정 |
| 환경 구분 / 사용자 지역 / 선택 리전 | 미정 |
| 현재 요금제 / 비용 한도 / 사용량 확인 담당 | 미정 — 결제정보·숫자는 실제 화면 확인 후 기록 |
| 인증 방식 / 가입 허용 여부 | 미정 — 이메일 코드 / 링크 / 비밀번호 / OAuth 등 |
| 메일 발신자 / SMTP 사용 여부 | 미정 — 자격증명은 기록하지 않음 |
| 웹 URL / 모바일 callback / 허용 redirect | 미정 — 선택한 인증 방식에 필요한 것만 |
| 핵심 데이터 / 소유권 / 보존·삭제 기준 | 미정 — 개인 / 팀 / 공개 데이터 구분 |
| 파일 사용 여부 / bucket / 공개 범위 / 포맷·크기 | 미정 |
| 직접 DB 조작과 서버 API의 역할 구분 | 미정 |
| 추가 기능 | 미정 — Edge Functions / Cron / Realtime / 확장 등 필요한 것만 |
| CLI·SDK 버전 / migration 방식 | 미정 — 구현 직전 확인 |
| 실제 서비스 연결을 시작할 조건 | 프론트엔드와 서버 독립 검증 완료 + 앱별 조건 |

비밀번호·secret key·서비스 계정 자격증명·개인 사진·실사용자 이메일·실제 연결 문자열은 넣지 않는다. 비밀 관리 도구의 **보관 위치 이름과 설정 여부**만 기록한다.

## 단계별 체크

### SB-00 — 범위와 사전 결정

- [ ] 앱의 선행 조건, 이번에 만들 환경, 프론트엔드와 서버 작업의 담당 범위를 확인했다.
- [ ] 위 프로젝트 값과 데이터 소유권·권한 표를 채웠다.
- [ ] 적용할 기능과 `해당 없음`을 구분하고 최신 공식 문서·변경내역을 확인했다.

완료 근거: 결정한 값과 남은 미정 항목. [방법](SETUP_GUIDE.md#sb-00)

### SB-01 — 프로젝트와 개발 환경

- [ ] 대상 조직·프로젝트·리전·요금제를 확인하고 개발 환경을 준비했다.
- [ ] DB 비밀번호를 안전한 보관 위치에 저장하고 project ref로 작업 대상을 구분했다.
- [ ] 로컬 개발을 쓰면 CLI·Docker·설정 파일을 준비했다. 기존 원격 프로젝트는 먼저 현황을 가져와 기준을 확보했다.

완료 근거: 개발 환경 식별 정보·연결 확인. [방법](SETUP_GUIDE.md#sb-01)

### SB-02 — 연결 정보와 키

- [ ] 값이 빈 앱/서버 env 예시와 입력 위치를 먼저 준비·안내했다. 사용자가 로컬 사본을 작성한 뒤 값 노출 없이 설정 여부를 확인했다.
- [ ] 앱에는 URL과 publishable key만, 관리자 권한은 서버에만 배치했다.
- [ ] 공개 환경변수와 서버 비밀값의 보관 위치를 구분하고 저장소·앱 산출물에 secret이 없는지 확인했다.
- [ ] 앱용 키와 사용자 로그인 세션의 역할을 구분했다. 키만 있다고 사용자 데이터에 접근할 수 있게 만들지 않았다.

완료 근거: 비밀값을 가린 설정 위치와 확인 결과. [방법](SETUP_GUIDE.md#sb-02)

### SB-03 — 인증과 메일

- [ ] 선택한 로그인 방식·가입 여부·세션과 재인증 정책을 설정했다.
- [ ] 이메일을 쓰면 템플릿 편집 가능 여부·발신 설정·수신 제한·만료·재발송을 확인했다. SMTP 미설정 때문에 막힌 항목은 미완료로 남겼다.
- [ ] 링크/OAuth를 쓰면 환경별 redirect와 모바일 callback을 설정하고 실제 복귀를 확인했다. 미사용이면 이유를 기록했다.
- [ ] 테스트 계정으로 성공·잘못된 인증값·만료·재시도·로그아웃을 검사했다.

완료 근거: 테스트용 계정 식별자와 인증 결과, 메일 설정값의 의미. [방법](SETUP_GUIDE.md#sb-03)

### SB-04 — 데이터베이스와 권한

- [ ] 필요한 테이블·필드·키·관계·제약을 설명하고 migration에 기록했다.
- [ ] API 노출·grants·RLS 정책을 데이터 구조와 함께 검토·적용했다.
- [ ] A/B/미인증으로 조회·생성·수정·삭제와 소유권 변경 시도를 검사했다. SQL Editor 관리자 성공으로 대신하지 않았다.
- [ ] 서버 전용 상태·필드와 함수의 호출 권한을 확인하고, 클라이언트 직접 쓰기로 서버 검증을 우회하지 못하게 했다.

완료 근거: schema/migration 경로, 권한 표의 실제 허용·거부 결과. [방법](SETUP_GUIDE.md#sb-04)

### SB-05 — 파일 보관

- [ ] 파일 기능 필요 여부를 확인하고 bucket의 공개 범위·허용 포맷·크기를 정했다.
- [ ] 파일 경로·소유권·업로드·조회·덮어쓰기·삭제 정책을 각각 설정했다.
- [ ] A/B/미인증, 잘못된 경로·크기·포맷으로 실제 파일 요청을 검사했다.
- [ ] DB 기록과 파일의 저장·삭제 순서, 중간 실패 복구와 미참조 파일 정리 책임을 정했다.

완료 근거: bucket 설정과 테스트 파일 결과. 파일 미사용이면 단계 전체 `해당 없음`. [방법](SETUP_GUIDE.md#sb-05)

### SB-06 — 서버 처리와 선택 기능

- [ ] 서버가 필요한 작업만 골라 요청·응답·오류·사용자 인증·권한 검증을 정했다.
- [ ] 중복 요청·동시 수정·부분 실패·삭제 재시도를 실제 API에서 검사했다.
- [ ] Cron·Realtime·확장 등은 필요할 때만 설정하고, 호출 주체와 실행 결과를 확인했다. HTTP 작업은 스케줄 실행 상태뿐 아니라 실제 응답 코드·본문을 확인하고, 공유 인증값은 원문 노출 없이 양쪽 일치를 대조했다.
- [ ] 관리자 키를 사용하는 처리에서도 사용자 소유권과 허용 작업을 따로 검증했다.

완료 근거: API 결과, 설정한 기능과 제외 이유. 서버 처리 미사용이면 단계 전체 `해당 없음`. [방법](SETUP_GUIDE.md#sb-06)

### SB-07 — 서버 독립 검증과 재현

- [ ] 폐기 가능한 로컬/검증 DB에서 migration으로 구조·권한을 재현했다.
- [ ] migration 밖의 Auth·SMTP·bucket·secret·함수·작업 스케줄 설정도 재현 방법을 남겼다.
- [ ] 앱 화면 없이 인증·API·DB·파일 권한·삭제를 검증하고 Advisor의 관련 항목을 확인했다.
- [ ] 프론트엔드에 환경 정보·데이터/오류 계약·테스트 결과를 전달했다. 비밀값은 전달 문서에서 제외했다.

완료 근거: 재현 결과와 서버 검증 기록. [방법](SETUP_GUIDE.md#sb-07)

### SB-08 — 실제 앱 연동

- [ ] 프론트엔드와 서버 독립 검증이 끝난 뒤 테스트 대역을 실제 연결로 바꿨다.
- [ ] 로그인·세션 복원 → 조회 → 저장 → 편집 → 삭제 순으로 하나씩 연결·확인했다.
- [ ] 오프라인·응답 유실·중복·세션 만료·계정 전환·충돌·탈퇴에서 데이터 보존과 권한을 검증했다.
- [ ] 실제 서버 확정과 화면상의 임시 상태를 구분하고 사용자 데이터·secret의 로그 노출을 검사했다.

완료 근거: 앱에서 수행한 실제 흐름과 실패 복구 결과. [방법](SETUP_GUIDE.md#sb-08)

### SB-09 — 운영 준비가 범위에 있을 때만

- [ ] 운영 환경의 도메인·메일·요금/사용량·알림 담당과 한도를 확인했다.
- [ ] DB와 파일의 백업 범위·복원 방법·보존 기간을 각각 확인했다.
- [ ] 삭제·장애·키 교체·복구 절차를 확인하고 운영 배포 완료 여부를 따로 기록했다.

완료 근거: 운영 인수 기록. 개발 환경 구축만 요청받았다면 `해당 없음 — 운영 준비 제외`. [방법](SETUP_GUIDE.md#sb-09)

## 단계별 진행 기록 양식

한 번에 현재 설정 항목 하나를 설명하고 아래 기록을 남긴다. 적용 전에 목적·위치·변경값의 의미를, 적용 뒤에는 검증 결과·다음 항목을 사용자에게 알려 준다. 사용자 직접 조작이 필요하면 행동을 안내하고 완료를 기다린다.

| 기록 항목 | 기입 내용 |
|---|---|
| 단계 / 세부 항목 / 시각 / 대상 환경 | SB-__ / 미정 |
| 상태 | 미착수 / 진행 중 / 사용자 작업 대기 / 검증 실패 / 완료 / 해당 없음 |
| 왜 필요한가 | 해결하려는 앱 동작 |
| 어디를 어떻게 설정했는가 | 화면·파일·migration과 비밀이 아닌 값 |
| 예상 결과 / 실제 결과 | 허용·거부·저장 상태를 구체적으로 비교 |
| 증거 | 비밀을 제거한 테스트 결과·스크린샷·파일 경로 |
| 사용자에게 설명한 내용 / 필요한 직접 행동 | 미정 |
| 되돌리기 또는 복구 | 해당 설정의 이전 값·복구 방법; 데이터 삭제로 대신하지 않음 |
| 다음 항목 / 시작 조건 | 미정 |

다른 앱으로 옮길 때는 이 파일·가이드·필요한 env 예시를 함께 복사하고, 앱 이름·환경·권한·기능 선택을 새로 채운다. 이전 앱의 완료 체크·project ref·정책 SQL·비밀값은 그대로 가져오지 않는다.
