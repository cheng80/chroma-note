# 사진 → 선화 스탬프: 모바일 후보 조사와 실제 변환 결과

> 현재 기준: 스타일 1 선에 원본 RGB 마스킹, 흰 배경, 색면·5색 축소·외곽선 강조 없음. **2026-09-11 사용자가 이 변환을 제품 기능으로 확정하고 입력·옵션 모듈화를 요청했다.** 아래 미채택·실험 후보 표기는 각 측정 당시 판단이며 현재 채택을 보류하는 조건이 아니다. 최신 기기 결과는 §11~12이며 앱 통합·Android·품질 회귀 검증은 별도로 남아 있다. 제품 모듈은 [chroma-lineart](../../modules/chroma-lineart/README.md)를 따른다.

> **산출물 가용성 — 2026-09-11:** 최신 결과 HTML 경로는 `data/line-art-20260910/ipad-resolution-final/index.html`이지만 현재 로컬 파일이 없다. 프로젝트·임시 보관 경로·휴지통 조회에서도 확인하지 못했다. 아래 역사적 링크를 현재 열 수 있는 증거로 안내하지 않으며, 복원 전에는 이 문서의 당시 수치와 파일의 존재 여부를 구분한다.

## 1. 결론

**현재 후속 결과:** 사용자 지시로 실측 기준을 **iPad mini 6**로 변경했다. 같은 기기의 카페 1024px·1536px 비교에서 원본 읽기부터 PNG 저장까지 반복 중앙값이 **0.223789→0.600536초**, **0.376747초 증가(+168.3%, 2.68배)**했다. 같은 표시 크기로 비교하면 선이 가늘고 정돈되는 변화는 있으나 얼굴·손의 정보가 크게 늘지는 않았다. [같은 배율의 전체·부분 확대 비교](data/line-art-20260910/ipad-resolution-final/index.html) · [결과 ZIP](data/line-art-20260910/ipad-resolution-final/results.zip). 상세 조건은 §12를 따른다.

**앞선 iPhone 결과:** 사용자가 원본색 선화에 “많이 좋아 진듯”이라고 평가하고 모바일 실폰 변환 시간 측정을 요청했다. §10 방식을 유지한 iPhone 실험에서 **40회 변환**, 원본 직접 처리 warm 중앙값 **0.056~0.209초**, 최초 모델 준비 **0.881초**를 확인했다. [실폰 결과 비교](data/line-art-20260910/iphone-review.html) · [측정·PNG 묶음](data/line-art-20260910/iphone-results.zip). 아래 최초 원출력의 품질 미달·모바일 미실행 문구는 그 시점의 기록이며, 이번 측정 중단이나 후속 개선 거절을 뜻하지 않는다. 앞선 iPhone 검증은 §11을 따른다.

**현재 결과:** 사용자 정정대로 색면·5색 축소·외곽 확장·내부 선 약화를 제거했다. 이전 디테일 선화에 원본 색을 그대로 마스킹한 5장이 최신 산출물이다. [전후 비교](data/line-art-20260910/line-color-review.html) · [전체 비교](data/line-art-20260910/line-color-sheet.png) · [결과·투명 선 ZIP](data/line-art-20260910/line-color-results.zip). §9의 5색 면 결과는 사용자 의도와 달라 채택하지 않았으며 §10을 따른다.

**앞선 디테일 결과:** 디테일 보존 요청에 따라 같은 스타일 1 모델에서 입력 축소를 줄여 5장을 다시 변환했다. 카페의 옷 무늬·손/컵·진열품은 더 살아났으나 얼굴 내부·숲의 식생 소실은 남았다. [전후 비교](data/line-art-20260910/detail-review.html) · [비교 이미지](data/line-art-20260910/detail-sheet.png) · [새 결과 ZIP](data/line-art-20260910/detail-results.zip). 조건·측정은 §8을 따른다.

**Informative Drawings의 공식 두 스타일로 사진 5장씩 실제 변환했지만, 모두 목표 품질에 미달했다.** 스타일 1은 큰 구도를 더 잘 남겼지만 음식 재료의 구분과 숲의 식생 표현이 무너지고, 목표의 정돈된 잉크 선·해칭을 얻지 못했다. 스타일 2는 구조선의 겹침과 세부 소실이 더 크다. 이 모델을 채택하지 않으며 Core ML 변환·앱 통합으로 진행하지 않았다.

사용자 후속 의견으로 **스타일 2는 제외**했다. 현재 산출물은 [원본·스타일 1 비교 페이지](data/line-art-20260910/review.html), [스타일 1 비교 이미지](data/line-art-20260910/contact-sheet.png), [스타일 1 결과 묶음](data/line-art-20260910/results.zip)이다. 로컬 파일이며 `data/`는 Git 제외다. 개별 원출력 10장과 실행 기록 및 [최초 전체 비교 묶음](data/line-art-20260910/all-styles.zip)은 실험 증거로 보존했다. 스타일 1의 품질 통과나 채택을 승인받은 것은 아니다. 생성 결과와 측정은 §7에 기록한다.

**이 모델을 최종 채택했다는 뜻은 아니다. 목표 삽화 수준과 iPhone·Android 실기기 실행을 모두 입증한 후보는 이번 조사에서 확보하지 못했다.** 이 모델의 장점은 의미·기하 정보를 학습한 선화 전용 구조와 작은 배포물이다. 가장 큰 약점은 예시처럼 정돈된 해칭·여백·대상별 선의 생략을 보장하지 못한다는 것이다. 작은 모델이라는 이유로 품질 기준을 낮추지 않는다.

사용자 후속 지시 **“모바일에서 사용 불가능 한건 다 제외하라”**를 필수 조건으로 적용했다. 클라우드 전용과 현재 모바일 제품 경로를 뒷받침하지 못하는 대형·복합 편집 구성은 추천 및 5장 비교 대상에서 제외했다. 모바일 이식 근거가 있는 작은 모델도 실제 기기 통과 전에는 **검증 후보**로만 취급한다. 실행 증거 부족을 기술적으로 영원히 불가능하다는 주장으로 바꾸지는 않는다.

## 2. 직접 확인한 목표와 충돌하는 요구

직접 열어 확인한 기준: [로그인 화면 삽화](../../design/images/generated-1788887279815.png), 1264×848.

`SHA-256: 5e55082243e1acf2a43c0b4b771b8eba317b83ceef7c63e423491a83935e257d`

- 크림색 종이 위 검정 잉크 선. 건물·중앙 문·양옆 창문·의자 두 개·테이블·오른쪽 화분이 명확하다.
- 큰 윤곽과 가는 내부 선이 구분되고, 기와·창틀·의자 다리처럼 반복되는 구조가 정돈되어 있다.
- 명암은 선택적인 해칭·검정 면으로 표현된다. 사진의 모든 질감을 같은 강도로 따라 그리지 않는다.
- 바깥 여백이 넓고 지면 묘사가 자연스럽게 끝난다. 사진 가장자리에서 사물을 자르거나 새로운 물체를 만들어 여백을 확보하는 것은 허용하지 않는다.
- **원본 사진이 함께 제공되지 않은 스타일 예시다. 사진 변환 성공 사례·구도 보존 증거·정답 이미지로 취급할 수 없다.** 이 건물의 형태를 인물·음식 사진에 옮겨서는 안 된다.

이번 순서는 **모바일 로컬 적합성 → 원본의 주요 내용 보존과 선화 품질 → 속도·메모리 절충**이다. 품질은 적합한 후보 사이에서 최우선이다. 모바일에서 쓸 수 없는 결과가 더 예쁘다는 이유로 추천을 되살리지 않는다.

| 요구의 충돌 | 이번 연구의 처리 |
|---|---|
| 장면 보존 ↔ 과감한 생략·여백 | 주요 사람·사물·시점·상대 위치는 유지. 잔무늬·미세 질감만 생략. 외곽 여백은 전체 결과의 동일 비율 축소로만 추가 |
| 일정한 스타일 ↔ 사진마다 다른 복잡도 | 사진별 수동 보정 없이 같은 가중치·해상도 규칙·후처리로 비교. 사진별 최고 결과 조합 금지 |
| 경량 모델 ↔ 작가가 선택한 듯한 해칭 | 작은 모델의 출력에 실제로 나타나는지 확인. 종이 질감이나 임의 사선 덧씌우기로 미달을 숨기지 않음 |
| 흑백 선화 연구 ↔ 기존 컬러 Ink 명세 | 이번 연구 평가는 새 선화 목표를 우선. 기존 앱·저장·색상 UI를 변경하거나 컬러 요구까지 검증 완료로 선언하지 않음 |

기존 [ADR](../../docs/adr/ADR-003-stamp-record-direction.md)·[AI 검증 계획](../../docs/05_AI_VALIDATION_PLAN.md)은 요구·권한의 경계만 확인했다. 그 문서의 특정 모델 순위, 과거 성공/실패, 프롬프트·seed·시간을 이번 후보 선정 근거로 사용하지 않았다. 신규 학습·LoRA·distillation도 이번 최단 실험에는 넣지 않는다. DreamLite는 사용자 요청으로 보류한다.

## 3. 최우선안의 근거와 정확한 범위

### 의미를 학습한 선화 전용 변환

Informative Drawings는 사진과 선화의 의미·기하 정보를 맞추는 학습 목표를 사용한다. 단순 밝기 경계 검출보다 이번의 ‘질감을 줄이되 무엇인지 알아볼 수 있는 선’에 가까운 문제를 다룬다. 그러나 학습 손실이 모든 사람 수·얼굴·공간 관계를 보존하는 강제 조건은 아니다. 논문 성능은 Chroma Note 합격률이 아니다. [CVPR 2022 논문](https://openaccess.thecvf.com/content/CVPR2022/papers/Chan_Learning_To_Generate_Line_Drawings_That_Convey_Geometry_and_Semantics_CVPR_2022_paper.pdf), [저자 프로젝트](https://carolineec.github.io/informative_drawings/)

저자 데모는 RGB 사진을 `ToTensor()`로 변환해 `Generator(3, 1, 3)` 하나에 입력한다. 별도 프롬프트·텍스트 인코더·VAE·확산 반복은 없다. CLIP·깊이 관련 학습 구성 전체를 모바일에 실을 필요도 없다. 데모에 올라온 두 스타일 중 제품에는 검증된 하나만 사용한다. [데모 코드](https://huggingface.co/spaces/carolineec/informativedrawings/blob/main/app.py), [공식 저장소](https://github.com/carolineec/informative-drawings)

### 모바일 경로와 사용 조건

- **iPhone 우선 경로:** 통과한 단일 generator만 Core ML로 변환한다. Apple의 공식 PyTorch 변환 경로는 존재한다. `ReflectionPad2d`, `InstanceNorm2d`, `ConvTranspose2d`의 정확한 옵션과 출력 크기·수치·연산 배치를 확인해야 한다. 이번 모델의 변환 성공·ANE 실행·처리 시간은 아직 모른다. [Apple 변환 문서](https://apple.github.io/coremltools/docs-guides/source/convert-pytorch-workflow.html)
- **Android 확장 경로:** 동일 원본 가중치·전후처리를 ONNX Runtime Mobile용으로 검증한다. 런타임은 iOS·Android를 공식 지원하지만 특정 모델의 연산 지원·속도를 보장하지 않는다. Core ML 파일 자체를 Android에 재사용할 수는 없다. 첫 시험부터 Core ML·ONNX·LiteRT를 모두 설치하지 않는다. [ORT Mobile](https://onnxruntime.ai/docs/get-started/with-mobile.html)
- **메모리:** 가중치 외에 원본 디코딩, feature map, 연산 버퍼·런타임이 필요하다. 512×512×64의 FP32 feature map 하나도 64 MiB다. 17MB 파일을 ‘17MB 메모리로 실행’한다고 설명해서는 안 된다. 타일 분할은 InstanceNorm의 통계와 경계를 바꾸므로 초기 해결책으로 사용하지 않는다. [모델 구조](https://github.com/carolineec/informative-drawings/blob/2349aee4daf7cb01d8de645b0bbb4f4392fd1395/model.py)

## 4. 대안 비교와 제외

모바일 검증 여지가 있는 경량 접근만 비교한다. 실제로 해칭이 없는 결과는 빠르더라도 목표 충족으로 판정하지 않는다.

|---|---|---|
| **TEED** | 저자가 약 58K 파라미터로 제시한 작은 경계 검출기. 선 추출은 가능하지만 참조 그림의 해칭·대상별 생략을 학습한 스타일 변환기는 아님 | 경량 경계 추출 대안. Informative Drawings보다 목표 표현에 직접적이지 않아 첫 시험에서 별도 설치하지 않음. 모바일 실측 미검증. [공식 코드·논문 연결](https://github.com/xavysp/TEED) |

## 5. 가장 짧고 결정적인 5장 실험

**아래는 실행 전에 정한 실험 설계다. 실제로 선정한 5장과 계획 차이, 생성한 10장의 판정은 §7을 따른다.** 앱 밖의 로컬 추론만 실행했으며 사진·출력은 Git 제외 `data/` 아래에 보존했다. 사용자 사진을 외부 데모에 업로드하지 않았다.

### 입력 5장

| ID | 서로 다른 사진 | 실행 전 원본에 기록할 핵심 사실 |
|---|---|---|
| L01 | 비스듬한 시점의 건물·문·창문·의자·화분 | 문·창문·의자 수, 앞뒤 겹침, 소실 방향. 목표 이미지와 비슷한 건물만 고르지 않음 |
| L02 | 실내 두 사람, 얼굴·손·컵·테이블이 보이는 장면 | 사람 두 명과 각자의 자세·시선·손/컵 관계, 얼굴을 알아볼 수 있는 특징 |
| L03 | 음식·식기·소품을 내려다본 사진 | 접시·컵·음식 수와 좌우 위치, 겹침, 탑뷰 유지 |
| L04 | 나무·잎·물 또는 하늘이 있는 자연 사진 | 큰 수목·지형 경계, 수평선·앞뒤 거리. 잎·반사는 생략 가능 |
| L05 | 역광 또는 어두운 복잡한 실내/거리, 작은 사람이 포함된 장면 | 작은 사람과 주요 사물 수, 겹친 구조·어두운 경계. 배경 질감에 인물이 묻히는지 |

5장에 세로·가로·저대비·풍부한 질감을 분산한다. 출력 보기 전에 에이전트가 보존할 대상과 허용 생략을 기록한다. 사진 설명은 평가용이며 모델 입력이 아니다.

### 실행 순서와 중단선

1. **실행 준비를 30분으로 제한한다.** 이는 작업 시간 상한이지 설치 완료 예상이나 성능 수치가 아니다. 공식 파일·라이선스·hash를 확인하고 저자 CPU 추론과 동등한 최소 실행만 준비한다. 오래된 전체 학습 환경, CLIP·깊이 네트워크, Gradio 웹 서비스는 설치하지 않는다. 환경 준비가 길어지면 `SETUP_BLOCKED`로 기록하고 대형 모델 설치로 우회하지 않는다.
2. 사진 방향·색공간을 정규화하고 **긴 변 512px, 종횡비 유지, 중앙 크롭·강제 정사각 늘이기 없음**을 적용한다. 축소 결과의 높이·너비를 필요한 최소 4배수까지 패딩하고 출력에서 패딩만 제거한다. 크림색 장식 여백을 모델 입력에 먼저 넣지 않는다. InstanceNorm 때문에 패딩 정책도 조건의 일부로 고정한다.
3. **`model.pth` 한 개, FP32, 동일 전후처리로 5장 각 1회.** RGB `[0,1]` 입력·한 채널 출력의 방향과 범위를 확인한다. 우선 후처리 없는 출력을 원본·목표 스타일 이미지와 나란히 비교한다. 이미지를 보기 좋게 만드는 threshold·해칭·종이 텍스처 튜닝을 먼저 하지 않는다.
4. 첫 스타일이 미달하면 **공식 `model2.pth`로 5장 전체를 한 번만** 비교할 수 있다. 이 또한 같은 모델 계열의 사전 고정 비교다. 사진마다 스타일을 골라 합격 세트를 만들지 않는다. 최대 10개 출력으로 종료하며 두 스타일 모두 미달이면 `QUALITY_FAIL`이다.
5. 승자가 있으면 어려운 사진 한 장을 같은 조건으로 1회 재실행한다. 모든 사진을 한 장의 비교표로 보고 선 굵기·명암 방식·빈 공간의 처리 방식이 일정한지 확인한다. 흰 바탕의 원출력도 보존한 뒤 제품 잉크색·종이색 적용본을 별도 비교한다. 이 장식 단계가 품질 미달을 통과로 바꿀 수 없다.

### 판정 — 평균으로 보존 실패를 가리지 않음

아래는 **후속 검증 진입을 위한 제안 기준**이며 사용자 승인된 출시 기준·통계적 품질 보증이 아니다.

- **보존 필수 5/5:** 주요 사람·사물의 누락/추가/교체, 사람 수 오류, 시점 변경, 주요 좌우·앞뒤 관계 역전이 없어야 한다. 작은 사람도 평가에서 제외하지 않는다.
- **선화 품질:** ① 읽히는 큰 윤곽과 내부 선 ② 사진 잔질감의 의미 있는 감소 ③ 명암이 필요한 곳의 정돈된 선/해칭·절제된 검정 면 ④ 빈 공간과 대상의 분리, 네 항목을 각각 `충족/부분/실패`로 채점한다. 각 사진이 모두 `충족`이어야 전체 목표 품질 통과다. 그림자 없는 사진에 해칭을 억지로 요구하지는 않는다.
- **일관성:** 한 가중치·한 설정으로 5장 전부가 같은 선화 계열로 읽혀야 한다. 어떤 사진은 연필 명암, 어떤 사진은 만화 외곽선에 머무르면 미달이다.
- **판정 범위:** 4장만 좋으면 ‘사진군 제한 가능성’이라는 발견일 뿐, 다양한 사진의 목표 달성으로 선언하지 않는다. 5장 통과도 큰 평가 세트·실사용 검증으로 가기 위한 신호다.
- **평가 방식:** 에이전트가 원본 대조 결과와 실패 위치를 명시한다. 자동 유사도 점수·목표 건물과의 픽셀 유사도·보기 좋은 썸네일만으로 통과시키지 않는다. 최종 제품의 사용자 비교·확인은 별도 필수 흐름으로 유지한다.

### 품질 통과 뒤에만 모바일 확인

| 순서 | 최소 검증 | 완료로 쓰면 안 되는 경우 |
|---|---|---|
| 1. iPhone 변환·동등성 | generator 한 개를 Core ML로 변환, 동일 5장의 원본 런타임 출력과 비교. FP32 기준을 남기고 FP16에서 가는 선 소실·검정 영역 확대 검사 | 파일 생성만 성공, synthetic tensor만 실행 |
| 2. iPhone 로컬 실행 | 우선 iPhone 14 Pro Max를 시험 기기로 제안. 실제 연결 가능 여부·OS 확인 후 사진 입력→출력, 최초/반복 시간·peak 메모리, 오프라인·취소·연속 10장 확인 | Mac·Simulator 시간을 iPhone 시간으로 기록, 서버 대리 추론, UI 멈춤·강제 종료 |
| 3. Android 확장 | 목표 실기기 하나를 정해 동일 원본→ONNX 경로로 같은 5장·로컬 전체 처리 비교. 미지원 연산·CPU fallback·시간·메모리 기록 | Core ML 성공을 Android 성공으로 기재, 모델 이름만으로 NPU 지원 판단 |

모바일 시간·메모리의 실제 값은 모두 **미측정**이다. 기존 목표·시험 기기를 참고할 수 있으나 새 후보의 성능으로 인용하지 않는다. 첫 모바일 판정에서는 **사진 정규화→선화→표시까지 10초 이내**를 잠정 대기시간 목표로 제안하고 실제 기기 자원·사용자 경험과 함께 판단한다. 초과한 결과는 빠르다고 소개하지 않는다. 모델 로드·첫 실행·반복 처리 시간은 분리한다.

Android까지 통과하기 전 상태는 `IOS_ONLY` 또는 `ANDROID_UNVERIFIED`다. 시뮬레이터 기능 확인도 별도로 남기며 실기기 성능을 대신하지 않는다. ONNX의 Core ML provider 등 가속기는 연산 지원·분할을 확인해야 하므로 ‘Core ML 사용’과 ‘전부 ANE 실행’을 같은 뜻으로 쓰지 않는다. [ORT Core ML 문서](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html)

## 6. 최우선안에 대한 적대 검토

| 반론·실패 가능성 | 판정 및 필요한 증거 |
|---|---|
| 17MB라서 선택했을 뿐, 예시처럼 그릴 능력이 없는 것 아닌가? | 유효한 반론. 작은 크기는 모바일 검증 비용의 근거일 뿐 품질 근거가 아니다. 원출력 5장에 해칭·질감 생략이 없으면 이 추천은 반증됨 |
| 사람을 새로 생성하지 않으니 사람 수는 자동 보존되는가? | 아니다. 약한 인물 윤곽 소실·얼굴 뭉침·중첩된 대상의 합쳐짐이 가능. L02·L05의 사전 annotation과 직접 대조 |
| 같은 모델이면 스타일도 항상 같은가? | 보장되지 않음. 입력 질감·대비·해상도와 정규화 통계의 영향이 남는다. 5장 전체와 재실행 결과를 함께 확인 |
| 후처리로 해칭을 추가하면 목표와 같아지는가? | 미입증. 그림자·표면 방향을 이해하지 못한 사선은 사진 질감을 다른 잡음으로 바꿀 수 있다. 첫 검증에 넣지 않음 |

## 9. 옅은 5색 면·큰 윤곽 강조 — 2026-09-10

**사용자 후속 정정으로 제외된 시도다.** 아래 당시 실행기는 [그때의 결과 ZIP](data/line-art-20260910/color-results.zip)에 보존했다. 현재 `colorize_lineart.py`는 §10의 선 마스킹 방식으로 교체했으므로, 아래 재실행 명령은 그 ZIP 안의 이전 실행기에만 해당한다.

사용자가 원본을 약 5색으로 단순화해 옅게 겹치고 사물 외곽은 굵게, 내부 선은 줄이는 후처리를 명시적으로 요청했다. 이 요청에 따라 기존 선화 위에 로컬 색면·선 레이어를 합성했다. 앞선 원출력만 비교하던 실험 경계를 이번 요청 범위에서 확장한 것이며 모델을 교체하거나 학습한 결과는 아니다.

[실행기](colorize_lineart.py)는 기존 설치된 OpenCV·NumPy·Pillow를 사용한다. 입력은 §8의 원본 정규화 PNG와 스타일 1 선화다. 사진별 동일 설정으로 처리하며 사진마다 다른 설정을 골라 묶지 않았다.

- **색면:** 축소한 원본의 잔질감을 줄이고 Lab 공간에서 색 차이에 가중치를 주어 5색을 추출·할당했다. 미세한 색 조각을 정리한 뒤 종이색에 25% 농도로 겹친다. 실제 색면 PNG는 5색이며 검정 선의 농도·경계 혼합까지 포함한 최종 PNG의 총 색 수가 5라는 뜻은 아니다.
- **선:** 원본의 큰 색·명암 경계와 겹치는 강한 모델 선만 굵게 하고, 작은 끊김을 닫은 뒤 반경 1px만큼 확장했다. 내부 선은 약한 값을 제거하고 최대 20% 농도로 남겼다. 단순한 첫 굵기 확장은 잔선을 과도하게 키워 제외했고, 원본 경계를 직접 다각형 선으로 그린 시도도 형태가 거칠어 제외했다. 최종 검토 대상은 `color-layer-clean/` 한 설정의 5장이다.
- **한계:** 이 방법은 의미 기반 사물 분할이 아니다. 그림자·문양·장식 경계도 굵어질 수 있고 사물 윤곽이 끊기거나 빠질 수 있다. 음식과 숲은 색 구분이 돌아왔지만 식재료·잎의 정확한 형태가 복원되지는 않았다. 모든 목표 품질을 통과했다고 판정하지 않는다.
- **산출물:** 사진별 합성 PNG, 5색 면 RGB PNG, 투명 배경의 선 RGBA PNG와 추출 5색·설정·hash·측정 기록. [실행 기록](data/line-art-20260910/color-layer-clean/run.json), [관찰](data/line-art-20260910/color-assessment.json). 원본·기존 선화도 비교 페이지에 모두 포함했다.
- **Mac 실측:** 색면/선 후처리만 사진당 0.195–0.597초, 파일 저장 포함 0.207–0.641초. 프로세스 peak RSS 201,834,496 bytes. 이 값은 기존 모델의 추론·로드·메모리를 포함하지 않으며 iPhone·Android 값도 아니다.
- **검증:** 자체 검사에서 색 수 ≤5, 큰 경계 선 확장, 내부 선 농도가 강조선의 1/4 미만, 반복 일치, 단색·무선 입력을 확인했다. 실제 5장의 색면은 모두 5색이고 출력 크기를 보존했다. 원본 선화 hash 대조, 분리 레이어 재합성, 실제 카페 입력 반복 일치와 결과 ZIP·링크를 검사했다. 앱 통합·모바일 실행은 하지 않았다.

## 10. 원본색을 선에만 마스킹 — 2026-09-10

색면·5색 축소·외곽 강조를 제거하고 §8의 `style1-detail/` 원출력으로 돌아갔다. 각 선 픽셀에 같은 위치의 정규화 원본 RGB를 그대로 넣고 흰 배경에 합성했다. 채도나 색상도 임의 변환하지 않는다. 색을 또렷하게 보이게 하는 처리는 `alpha = min(255, round((255 - line) × 1.8))`뿐이다. 픽셀별 농도 조절이므로 선의 비영역/영역 경계를 확장하거나 내부 선을 따로 줄이지 않는다. 밝은 원본색의 선은 흰 배경에서 약해질 수 있다.

실행기 [colorize_lineart.py](colorize_lineart.py)에서 기존 영역 추출·팔레트·선 확장 코드를 제거했다. 후처리는 Pillow만 사용하며, 모델을 다시 실행하지 않았다. Mac의 마스크·합성만 사진당 1.0–4.3ms로 측정했으며 모델 추론·디코딩·파일 저장·모바일 실행 값은 아니다. [실행 기록](data/line-art-20260910/source-color-lines/run.json)

실제 5장에서 **이전 선화와 비영역/영역 픽셀 일치**, **선 픽셀 RGB가 원본과 완전 일치**, **색이 없는 곳의 흰 배경**, **크기 유지**를 검사했다. 투명 선 PNG는 완전 투명한 픽셀의 숨은 RGB를 지웠다. 자체 검사에서 반복 일치와 크기 불일치 거부도 확인했다. 이전 5색 결과와 앱 코드를 덮어쓰지 않았다. iPhone·Android 실행과 제품 품질 통과는 아직 미검증이다.

```sh
python colorize_lineart.py --self-test
python colorize_lineart.py --input data/line-art-20260910/style1-detail --output data/line-art-20260910/repeat-source-color-lines
```

## 11. 현재 선화의 iPhone 실폰 시간 측정 — 2026-09-10

사용자가 §10 결과 개선을 인정하고 실폰 성능 측정을 요청했다. 같은 스타일 1 가중치·원본색 마스킹·선 농도 1.8을 사용하며, 선화 디테일을 줄이거나 색면·5색 축소·선 확장을 되살리지 않는다. 제품 앱 연결이 아닌 실험 전용 실행기다.

### Core ML 변환 검증

- [변환 실행기](export_lineart_coreml.py)는 기존 저자 코드·가중치 SHA-256을 확인하고 `Generator(3,1,3)`을 Core ML ML Program FP16으로 변환했다. 입력 `image`는 Float32 NCHW, 출력 `line`은 Float32 NCHW다. 현재 5장에 필요한 `[1,3,428,640]`, `[1,3,1024,832]` 두 모양을 열거했으며 임의 사진 크기 전체를 지원하는 제품 모델은 아니다. [Apple 변환](https://apple.github.io/coremltools/docs-guides/source/convert-pytorch-workflow.html), [열거형 입력 모양](https://apple.github.io/coremltools/docs-guides/source/flexible-inputs.html)
- `coremltools 9.0`, `torch 2.14.0`. 변환 도구가 이 Torch 버전을 공식 시험하지 않았다는 경고가 나왔지만 실제 변환·로드·5장 추론·수치 대조를 완료했다. 실패나 경고를 숨기고 지원 버전으로 간주하지 않는다.
- 정규화 입력은 §8과 같은 PNG이며 새 PyTorch 결과가 기존 선화와 픽셀 단위로 같은지 먼저 확인했다. FP16 Core ML과 PyTorch의 평균 오차는 사진별 **0.000368~0.000636**, 8비트 선화 평균 차이는 **0.104~0.154단계 / 255**다. 두 입력 모양·유한값·출력 범위를 통과했다. 수치 일치는 새로운 품질 채택 판정을 대신하지 않는다.
- [변환 기록](data/line-art-20260910/coreml-fp16/conversion.json), [변환 모델](data/line-art-20260910/coreml-fp16/LineArt.mlpackage). 컴파일된 `LineArt.mlmodelc` 파일 합계 **8,617,493 bytes**. 모델 변환·사전 컴파일은 Mac에서 했으며 휴대폰 변환 시간에 포함하지 않는다.

## 12. iPad mini 6에서 1024px→1536px 비교 — 2026-09-10

사용자는 해상도를 높여 화질 개선과 추가 시간을 확인하도록 요청한 뒤 **“실 테스트는 이제 아이패드미니6로 하자”**로 기준 기기를 변경했다. 이후 실제 기기 테스트는 iPad mini 6를 사용한다. 이전 iPhone 수치를 새 비교의 기준값으로 사용하지 않고 iPad에서 1024px도 새로 측정했다.

### 조건과 시간

- 기기: **iPad mini 6 (`iPad14,1`) / iPadOS 26.6.1**, USB 연결, 배터리 100%, 저전력 모드 꺼짐. 전후 OS 열 상태는 모든 12회에서 `nominal`이다.
- 같은 L02 원본(1654×2044), 같은 가중치·FP16 모델·원본색 마스킹·농도 1.8. ImageIO 원본 읽기/축소·reflection padding·8비트 마스크·색 합성 방식은 유지했다. 이번에는 해상도만 변경했으며 새로운 Lanczos 전처리나 실수 마스크 합성을 함께 적용하지 않았다.
- 입력/출력: **829×1024 → 1243×1536**. 패딩된 모델 입력은 `[1,3,1024,832]`, `[1,3,1536,1244]`다. 원본 한계가 640px인 나머지 네 사진을 인위적으로 확대하지 않았다.
- 같은 서명 앱·모델을 설치하고 해상도별 새 프로세스로 실행했다. 각 **최초 1회 + warm 5회**. 1024px → 1536px 순서이며 모든 변환에서 실제 모델을 호출했다. 시간은 원본 읽기·축소·텐서·예측·색 합성·해당 해상도 PNG 저장까지다. UI·사진 선택·진단 파일·모델 사전 컴파일은 제외했다. 비교 화면에서 1536px 이미지를 같은 표시 크기로 줄이는 작업은 이 기기 시간 밖이다.

| 항목 | 1024px | 1536px | 증가 |
|---|---:|---:|---:|
| 첫 변환(모델 준비 제외) | 0.301172초 | 0.697319초 | +0.396147초 |
| **반복 5회 중앙값** | **0.223789초** | **0.600536초** | **+0.376747초, +168.3%, 2.68배** |
| 반복 범위 | 0.220625~0.230552초 | 0.564379~0.658395초 | — |
| 추론 중앙값 | 0.149374초 | 0.450550초 | +0.301176초 |
| 원본 읽기·축소 중앙값 | 0.024684초 | 0.035572초 | +0.010889초 |
| 색 합성 중앙값 | 0.009078초 | 0.019087초 | +0.010009초 |
| PNG 인코딩·쓰기 중앙값 | 0.037719초 | 0.080739초 | +0.043020초 |
| OS 앱 프로세스 peak footprint | 87.3MiB | 177.6MiB | +90.3MiB |

단계별 중앙값의 합계는 전체 중앙값과 다를 수 있다. 모델 준비는 첫 프로세스 **2.282608초**, 다음 프로세스 **0.199089초**였다. 같은 모델을 순서대로 실행해 시스템 캐시 상태가 다르므로, 이 준비 시간 차이를 해상도의 영향으로 해석하지 않는다. 1024px 첫 사진은 준비+변환 약 2.584초다.

메모리는 `TASK_VM_INFO`의 프로세스 생애 최대 physical footprint이며 진단 이미지·미리보기까지 포함한다. 별도 시스템 서비스에 할당된 자원을 포함하는 기기 전체 또는 모델 전체 메모리 측정이 아니다. RSS peak는 각각 81.0MiB·129.9MiB였다. 짧은 12회 시험이며 장시간 부하/발열 시험은 아니다.

### 눈으로 확인한 변화

두 결과를 829×1024로 맞춘 뒤 얼굴·손/컵·옷 무늬·앞쪽 진열대를 같은 사각형과 같은 배율로 확대했다. 1536px의 원래 PNG도 별도로 제공한다.

- 선이 더 가늘고 정돈되고, 옷의 잔무늬·기물 가장자리 표현이 일부 달라진다. 같은 표시 크기에서 소폭 변화다.
- 얼굴 내부의 생략, 손가락·컵 주변의 정보 부족이 뚜렷하게 해결되지는 않았다. 의미 있는 세부가 크게 복원됐다고 판정하지 않는다.
- 이 카페 사진에서는 처리 시간을 2.68배 쓰는 데 비해 디테일 개선이 작다. 1536px 실행 가능성을 확인한 결과이며 기본 해상도 변경이나 품질 채택 승인으로 간주하지 않는다.

### 검증·재현

- 모델 변환은 기존 모델에 새 입력 모양을 추가했다. 첫 Mac CPU 참조 검증은 1536px에서 **종료 코드 137로 중단**되어 검증 완료로 기록하지 않았다. 메모리 부담을 줄이기 위해 별도 실행에서 참조를 PyTorch MPS FP32로 옮겨 검증했다. 이 실행은 5장 모두 통과했고, 카페 1536px에서 Core ML 대비 평균 오차 **0.000380**, 8비트 선화 평균 차이 **0.096/255**였다. [완료된 변환 검증](data/line-art-20260910/coreml-1536-verified/conversion.json)
- 실제 설치된 모델과 재검증 모델은 명세가 동등하고 가중치가 byte 단위로 같다. 파일 직렬화 시 맵 순서가 달라질 수 있어 명세 파일 자체의 SHA 차이를 모델 차이로 취급하지 않는다. 실제 iPad 정규화 입력으로 Mac Core ML과 iPad 출력을 다시 대조했으며 선화 평균 차이는 **1024px 0.00762/255, 1536px 0.00771/255**, 최대 차이는 모두 **1/255**다. [기기 수치 대조](data/line-art-20260910/ipad-resolution-final/model-parity.json)
- 12회 모두 크기·유한값·범위·단계 시간 합계·native 색 합성을 확인했다. 해상도별 6회 결과는 픽셀 단위로 일치하며, 선 RGB 합성은 기존 Python `compose`와 일치한다. [검증 요약](data/line-art-20260910/ipad-resolution-final/summary.json)
- [1024px 원기록](data/line-art-20260910/ipad-1024-run/run.json), [1536px 원기록](data/line-art-20260910/ipad-1536-run/run.json), [전체·같은 배율 확대 비교](data/line-art-20260910/ipad-resolution-final/index.html), [로컬 결과 ZIP](data/line-art-20260910/ipad-resolution-final/results.zip). 브라우저에서 15개 이미지 로드와 390px 화면 가로 넘침 없음을 확인했다.

재실행: `export_lineart_coreml.py --edge 1536 --reference-device mps --data <data> --output <새 모델 경로>`로 변환·검증한다. 컴파일 후 `ios-lineart/build.py --model <LineArt.mlmodelc> ...`로 동일 실행기를 빌드한다. `BENCH_CASE=L02`, `BENCH_EDGE=1024` 또는 `1536` 환경변수를 실제 기기 실행에 전달하면 각 6회 변환한다. 환경변수를 생략하면 §11의 기본 40회 검증 경로를 유지한다. [비교 생성·검증 실행기](compare_lineart_resolution.py)에 `--baseline <1024 실행 폴더> --detail <1536 실행 폴더> --output <새 비교 폴더>`를 전달한다.
